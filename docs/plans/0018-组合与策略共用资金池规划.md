## 0. 结论摘要

1. **#4 的 24% 利用率不是「资金被静态切走」造成的**。#4 是「单组合 + 单策略 + `capital_ratio=1`」，没有第二个策略或组合可以接走这笔钱。真正的原因是：`max_positions=10` × `max_order_amount=50 万`，在 #4 当前配置下推导出的可部署上限是 **500 万**（案例值，不是硬编码；换配置就变），而权益已经涨到 3,888 万，理论上限就是 12.9%。任何资金池在单策略下都是空转。
2. **主从策略不应做「共用资金池」**。slave 的开仓前提是 master 已持有；把 master 的钱挪给 slave，会削弱 slave 自己的信号源，还会让 master 因资金不足无法开仓 → slave 永远等不到授权。主从应该保留为「信号门禁」，另加「master 优先预留」，而不是钱包共享。
3. 真正值得做的是**三层动态额度**：
   - 会话层（多组合）：按「可执行机会 + 近期资金需求 + 风险余量」分配；
   - 组合层：按策略需求分配，主策略优先预留；
   - 订单层：把固定的 `max_order_amount` 改成「权益百分比 / 容量上限」双约束。
4. **额度不是现金划转**。新方案只分配「本窗口可花额度」，现金仍留在组合账本里，成交时才扣额度和现金。这能从根上避免实盘把 A 的钱记到 B、现金被扣成负数、分币舍入对不平。
5. **验收目标**：以 #4 旧口径（24.5%）为下界、#14 无上限口径（54.4%）为不可实现上界，目标利用率 **35%–45%**，最大回撤 ≤ 8%，且不突破层 1 容量与单票集中度。不能靠调参硬凑。

### 1.3 现有实现的能力边界

- 会话资金池只重分**虚拟现金**（`account.cash`），不重分持仓、不碰柜台资金；未成交买单预留不参与总额；分币舍入没有最大余数法。
- 真实侧缩量仍按 `initial_capital` 占比切（`_capital_share`），与资金池权重不一致。
- 回测 `run_multi` **不共享现金**，各组合花自己的钱；`run_multi` 的 docstring 里「共享可用额 / 从其他组合转移差额」是过期描述，以代码和单测为准。
- 策略可下单额固定为 `capital_ratio × min(组合净值, equity_cap)`，策略之间没有借用机制。
- `max_single_position_pct` / `min_cash_reserve_pct` 只在实盘接线，回测恒为 `None`。

## 2. 问题拆解：24% 到底卡在哪

单策略下的单笔目标金额：

```text
target_amount = single_open_ratio × capital_ratio × min(equity, equity_cap)
order_amount  = min(target_amount, max_order_amount)
max_gross     = max_positions × order_amount
utilization   = max_gross / equity
```

#4 的参数：`single_open_ratio=10%`、`capital_ratio=1`、`max_positions=10`、`max_order_amount=50 万`。

- 权益 200 万时：单笔目标 20 万 < 50 万，10 个槽位可满仓，利用率上限 100%。
- 权益 500 万时：单笔目标 50 万 = 上限，10 个槽位 = 500 万，上限 100%。
- 权益 3,888 万时：单笔目标 388 万，但被压到 50 万；10 个槽位 = 500 万，上限 **12.9%**。

结论：

1. **资金池解决不了单策略的单笔硬上限**。没有第二个策略来「借走」闲置资金，池子里只有它自己。
2. **必须同时改两件事**：
   - `max_order_amount` 从固定金额改为「权益百分比 + 容量上限」；
   - 槽位数从 10 提高到容量允许的数量（例如 20），否则单笔上限放大后仍然受槽位限制。
3. 资金池的价值在**多策略 / 多组合竞争同一笔钱**时体现：A 没信号、B 有信号，B 可以临时多用；而不是在 #4 这种单策略里变魔术。

## 3. 设计原则

1. **额度而非现金**：分配结果是一张「本日可花额度表」，不是把 `account.cash` 从 A 改到 B。成交时同时扣「额度」和「现金」，任一不足即缩量。
2. **硬约束前置**：回撤、日亏、熔断、现金下限、单票集中度、容量预算，全部作为分配的**上限**参与计算，而不是事后再告警。
3. **无前视**：需求估计只用「上一交易日前 N 个完整交易日」的数据；容量使用当前 bar 截至当下的累计成交量（因果）；不得使用当日全天量或未来价格。
4. **确定性**：同一输入必须得到同一分配结果；排序键必须有唯一兜底（如 `strategy_id`），禁止依赖字典遍历顺序。
5. **默认关闭、可回退**：所有新逻辑挂在 `capital_pool_enabled` / `capital_pool_mode` 下；关闭时与现有行为逐位一致（含事件、快照字段）。
6. **账实可解释**：任何额度变化都要能写出「谁、多少、为什么、依据哪一版规则」。

## 4. 总体架构：三层额度

```text
会话层  SessionPool        Σ 组合现金 − 在途预留 − 现金下限 = 可分配池
   │
   ├── 组合 A 额度  Budget_A  （按机会/需求/风险分配，不是现金划转）
   │      ├── 策略 A1 额度
   │      └── 策略 A2 额度（主从：master 优先预留）
   │
   └── 组合 B 额度  Budget_B
```

三层职责：

| 层 | 作用域 | 解决的问题 | 数据来源 |
|---|---|---|---|
| L3 会话池 | 同一会话的多个组合 | 组合间闲置资金调剂 | 组合权益、现金、信号需求、容量、风险余量 |
| L2 组合预算 | 同一组合的多个策略 | 策略间静态 `capital_ratio` 切分 | 策略需求、槽位、主从关系 |
| L1 订单额度 | 单笔订单 | 固定 `max_order_amount` 导致衰减 | 权益百分比、20 日 ADV、容量预算 |

### 4.1 核心数据结构

```python
@dataclass
class CapitalPlan:
    version: str                 # 例：v1-demand5d-l0.6-floor0.05-cap0.50
    trade_date: date
    total_available: Decimal     # 可分配池（已扣在途/下限）
    session_reserve: Decimal     # 不可动的现金下限
    portfolios: dict[int, PortfolioBudget]
    strategies: dict[int, StrategyBudget]
    code_quotas: dict[str, list[CodeQuota]]   # 同日同票跨组合/跨策略配额
    reasons: list[dict]          # 每个数字的来源，落事件表
```

```python
@dataclass
class PortfolioBudget:
    budget: Decimal          # 本窗口授权额度
    floor: Decimal           # 保留额度（不可被其他组合借走）
    demand_score: Decimal
    risk_factor: Decimal
    max_gross: Decimal
    reason: str
```

额度生命周期：

```text
allocate()  → budget
submit()    → reserved += 订单未成交金额
fill()      → reserved -= 本次成交额；used += 本次成交额；cash -= 成交额
cancel()    → reserved -= 剩余未成交金额
day_end()   → used/reserved 清零，重新计划
```

**关键**：`reserved` 与 `used` 分开记。`used` 是已花掉，`reserved` 是已承诺未成交。额度检查用 `budget − used − reserved`。

## 5. 动态分配算法

### 5.1 需求估计（不能只看静态权重）

对每个策略 `j`，定义四个量：

```text
slot_gap_j       = max(0, max_positions_j − 当前持仓数_j)
target_value_j   = min(single_open_ratio_j × 策略资金, 单笔上限_j)
signal_count_j   = 上一交易日收盘后仍未执行的 OPEN/ADD 信号数
                 + 最近 N 日平均每日新 OPEN/ADD 信号数
requested_avg_j  = 最近 N 个完整交易日的「请求买入金额」均值（含被容量/上限缩量的请求）
residual_j       = 当前未成交买入残量的名义金额
```

```text
executable_j = min(slot_gap_j, signal_count_j) × target_value_j
demand_j     = max(requested_avg_j × 0.5 + residual_j, executable_j)
```

说明：

- `N` 默认 5 个交易日，窗口只取 `< 今日` 的完整交易日，避免前视。
- `requested_avg` 用「请求金额」而不是「成交金额」，否则被旧上限压过的策略会永远显得没需求。
- `executable_j` 把「有信号但没槽位」和「有槽位但没信号」区分开，避免给空槽位多的策略白送钱。
- 需求再按「该策略的理论最大毛敞口」归一化，防止大策略永远赢：

```text
max_gross_j = max_positions_j × min(single_open_ratio_j × 策略资金, 单笔上限_j)
demand_ratio_j = clamp(demand_j / max_gross_j, 0, 1)
```

### 5.2 组合权重

先算风险份额（复用现有回撤上限，但改成动态）：

```text
risk_share_i = (1 / max_drawdown_i) / Σ_j (1 / max_drawdown_j)   # 现有 risk_budget 口径
```

再算需求份额：

```text
demand_share_i = demand_i / Σ_j demand_j
```

最终权重：

```text
raw_i = λ × demand_share_i + (1 − λ) × risk_share_i
```

- `λ = 0.6`：更偏向「现在有机会、有需求」的组合；`λ=0` 退化为现有回调倒数，`λ=1` 退化为纯需求。
- 对 `demand_i = 0` 的组合，`raw_i` 只保留风险份额的「保留值」，但不强制发钱；未使用的额度留在池里。

然后做**带上下限的水位归一化**（water-filling）：

```text
floor_i = min(need_i, min_share × total)      # 默认 min_share = 5%
cap_i   = max_share × total                   # 默认 max_share = 50%
```

迭代：先给每个活跃组合 `floor_i`，剩余额度按 `raw_i` 分配；超过 `cap_i` 的截断，截断出来的额度再按 `raw_i` 分给未达上限的组合，直到收敛。全不活跃时额度留在池里，不强行分完。

最后做业务上限：

```text
budget_i = min(
    water_filled_i,
    need_i,                                  # 理论最大需求
    max_gross_i × risk_factor_i,             # 风险余量
    free_cash_i + 可借入额度,                 # 本组合现金 + 池内可借
    target_utilization_i × equity_i          # 目标仓位上限，默认 95%
)
```

### 5.3 「抢钱」仲裁：同日同票、同日多策略

必须分两级处理，顺序不能反：

1. **先按股票聚合容量**。同一 `code` 在同一天的所有组合/策略买单，共享层 1 的 `CapacityBudget`（`bar` / `day` / `5d` 三重预算取最小）。现有回测多组合已经共用同一个 `CapacityBudget` 实例，实盘也应保持一个会话一个实例。
2. **再在需求方之间分配该股票的配额**：

```text
Q_code = capacity(code, bar)                       # 股数
w_p    = priority_p × demand_p(code)               # 同票需求权重
qty_p  = floor(Q_code × w_p / Σw / lot) × lot      # 按手向下取整
余数按 (priority desc, demand desc, portfolio_id) 依次补 1 手
```

3. **主从同票**：master 先拿，slave 只能拿剩余。因为 slave 的开仓前提是 master 已持有，不能反向抢。
4. **同日多策略同票**：同一组合内先按策略 `priority` 降序，再按信号强度/需求降序，最后按 `strategy_id` 兜底。
5. **失败留痕**：所有被配额拒绝的订单记 `code_quota_contention`，包含 `Q_code`、各 `w`、最终 `qty`，便于复盘「是不是被同门抢了」。

同票以外的排序（BUY 阶段）：

```text
SELL（含止损/止盈/移动止损）→ 全部先执行
BUY 排序键：(组合 priority desc, 策略 role=master 优先, demand_ratio desc,
             signal_strength desc, code, strategy_id)
```

这样可以保证：卖出释放的现金先回池，再按优先级分配给买入；同一根 bar 内不会出现「先买的把后卖的钱花了」的时序错位。

### 5.4 单组合内主从策略：做动态额度，不做资金池

**结论：不建议做「主从共用资金池」。**

原因：

1. **授权闭环**：slave 只能在 master 已持仓后开仓。master 的钱被 slave 借走 → master 可能买不到 → slave 永远等不到授权，形成死锁。
2. **滞后一个 bar 是因果约束，不是资金问题**。资金池不能让 slave 提前知道 master 会成交；强行同 bar 跟买会引入前视。
3. **风控归因**：master 的止损/全平会触发 slave 全平；如果两者共用钱包，一次 slave 的亏损会改变 master 的可用额度，进而改变 master 的止损后行为，风险链条不可解释。

推荐做法：

```text
组合可分配额度 B_p
master 预留 = min(master 的理论最大需求, B_p × master_reserve_ratio)
slave 额度  = max(0, B_p − master 预留 − 组合现金下限)
```

- `master_reserve_ratio` 默认 0.6（master 自己的 `max_positions × target_value / B_p` 与 0.6 取小）。
- master 当天未用完的**未承诺**额度，可在次日计划时借给 slave；当天不借，避免 master 盘中出现新信号时无钱可用。
- slave 的额度还要叠加现有门禁：master 当前持有该 code；master 全平 → slave 下一根自身周期 bar 全平。
- 滞后问题只能缓解，不能消除：
  - master/slave 用同一周期；
  - slave 在自身下一根 bar 开盘按优先级执行（现有行为）；
  - 记录 `slave_lag_cost`（master 成交价到 slave 成交价的滑点），作为策略评估指标；
  - 不建议为了消除滞后而让 slave 与 master 同 bar 成交，那会引入前视。

## 6. 风险约束：作为分配上限，而不是事后告警

### 6.1 风险余量因子

对每个组合：

```text
dd_i = 1 − equity_i / peak_i
dd_factor_i = clamp((max_drawdown_i − dd_i) / (0.5 × max_drawdown_i), 0, 1)

day_loss_i = max(0, −daily_pnl_i) / daily_loss_base_i
daily_factor_i = clamp((daily_loss_limit_i − day_loss_i) / (0.5 × daily_loss_limit_i), 0, 1)

breaker_factor_i = 0 if 熔断/日亏暂停/会话级熔断 else 1

risk_factor_i = min(dd_factor_i, daily_factor_i, breaker_factor_i)
```

含义：

- 回撤达到上限的一半之前，额度不受影响；超过一半后线性收紧；达到上限时新开仓额度为 0。
- 日亏同理：达到日亏上限的一半后开始收紧，达到上限当天不再给新额度。
- 熔断/暂停直接 0。
- 这是**分配上限**，原有的事后熔断逻辑继续保留，形成双保险。

### 6.2 现金下限

```text
portfolio_floor_i = min_cash_reserve_pct_i × equity_i
session_floor     = pool_cash_floor_pct × Σ equity_i
pool_free         = Σ cash_i − Σ 在途买入预留_i − Σ portfolio_floor_i − session_floor
```

- `pool_free < 0` 时，本日不分配，只记录 `pool_negative`。
- 任何组合的额度不得超过 `cash_i − portfolio_floor_i − 本组合在途买入预留`，除非从池内显式借入；借入也要受 `pool_free` 约束。

### 6.3 集中度

- 组合级单票：`max_single_position_pct`，默认 10%。
- 会话级单票（新增）：同一 `code` 在会话内所有组合的合计市值 ÷ 会话总权益 ≤ `session_code_concentration_pct`，默认 15%。
- 单策略毛敞口：`max_positions × target_value`，作为策略额度的硬上限。
- 组合目标仓位：`target_utilization`，默认 95%，防止把现金下限也吃掉。

## 7. 回测实现

### 7.1 模块与接入点

新增纯函数模块 `main/core/engine/capital_pool.py`：

```python
def build_plan(context: PlanContext) -> CapitalPlan: ...
def allocate_code_quota(plan, code, requested: dict[int, int], capacity_qty: int) -> dict[int, int]: ...
def risk_factor(portfolio, state) -> Decimal: ...
def largest_remainder(total: Decimal, weights: dict[int, Decimal]) -> dict[int, Decimal]: ...
```

接入点：

- `BacktestEngine.run` / `run_multi`：每个交易日首根 bar 之前调用 `build_plan`，把 `plan.strategies[sid].budget` 注入 `StrategyContext`。
- `Portfolio._strategy_fund`：优先返回 `min(legacy_fund, budget_remaining)`；关闭资金池时仍返回原值，保证逐位一致。
- `ExecutionEngine`：在现有 `max_order_amount` 之后追加 `budget_remaining` 检查；被额度缩量的订单记 `capital_budget_shrink`，残量保留原有队列/TTL。
- `capacity.py`：不改算法，只保证多组合共用同一个 `CapacityBudget` 实例；额度分配发生在容量预算之前，容量仍可继续缩小。

### 7.2 再平衡时点与频率

- **主频率：日频**。每个交易日首根 bar 之前生成当日 `CapitalPlan`。
- **计划有效期：当日**。当日新出现的信号只能从「本组合剩余额度 + 会话未分配额度」里申请，不能回收其他组合已承诺的额度。
- **盘中再借（可选，默认关）**：`pool_intraday_relend=true` 时，在每根 bar 结束后，把「未承诺且未使用」的额度按优先级重新分配给有未满足需求的策略；只使用截至该 bar 的信息，记录 `relend_round`。
- **`pool_rebalance=first_bar_only`**：只在会话启动/回测开始时分配一次，用于对照旧行为。
- 不做「按事件逐笔重算权重」，避免抖动和不可复现。

### 7.3 可用资金口径（无前视）

```text
available = Σ portfolio.cash
          − Σ 未成交买入预留（含容量切片残量）
          − Σ 费用预留
          − Σ 组合现金下限
          − 会话现金下限
```

- 需求估计只用「上一交易日及更早」的 N 个完整交易日；当日 bar 的数据只能用于容量和成交，不能用于预测当日需求。
- 单笔上限的 ADV 口径：用「上一交易日往前 20 个完整交易日」的成交额均值，不用当日全天量。
- 容量模型的 `bar` 预算使用当前 bar 截至当下的累计量，属于因果；`day`/`5d` 预算同样只累计到当前 bar，不使用未来 bar。
- 禁止用「当日收盘后的信号」去回填当日开盘的额度；日线策略的 signal 在下一交易日执行，正好满足这一点。

### 7.4 与层 1 容量切片 / 残量顺延的关系

- 额度是「资金授权」，容量是「市场能成交多少」，两者取小。
- 容量把订单切成残量后，残量继续占用原额度；额度不会因为「这 bar 没成交」而立刻释放，避免下一 bar 重复分配。
- 残量超过 `capacity_slice_ttl_bars` 作废时，同时释放额度。
- 容量不足导致的缩量记 `capacity` 事件，额度不足导致的缩量记 `capital_budget` 事件，两者分开统计，避免混淆「没钱」和「没量」。
- 不允许用资金池额度去突破 `CapacityBudget.allow()` 的返回值。

### 7.5 口径版本记录

在 `params_snapshot` 增加：

```json
{

    "version": "v1-demand5d-n5-l0.6-floor0.05-cap0.50",
    "enabled": true,

    "lambda": 0.6,
    "rounding": "largest_remainder",
    "risk_rule": "dd_half_linear",

```

同时把当日计划写入回测快照/事件，至少包含：每个组合的 `budget / floor / demand_score / risk_factor / max_gross`，每个策略的 `budget / used / reserved`，以及每个同票配额。

推荐在 `backtest_decision_events` 复用记录：

## 8. 实盘实现

### 8.1 三处在途 / 账实风险的处理

#### 风险一：未成交买单占用未计入池

现状：`Σ cash` 不含已提交未成交买单，虚拟现金在成交回填时才扣。若日初按 `Σ cash` 重分，旧买单成交后可能把某组合扣成负数。

处理：

```text
open_buy_reserved_i = Σ(未成交买单剩余量 × 委托价) + Σ(容量切片残量 × 参考价)
pool_free = Σ cash_i − Σ open_buy_reserved_i − Σ fee_reserve_i − floors
```

- 计划生成前必须扣在途预留；`pool_free < 0` 时本日不分配。
- 每笔订单提交时 `reserved += 未成交金额`；成交时 `reserved -= 本次成交额`、`used += 本次成交额`；撤单/拒单释放剩余。
- 成交回填前做硬校验：`cash_i − 本次成交额 ≥ 0`；若为负，记 `negative_cash_guard`，立即冻结该组合的新买入，次日计划优先补足。正常路径下，预留充分时不应触发。

#### 风险二：真实额度仍按 `initial_capital` 占比切

现状：`_capital_share()` 用启动时的 `initial_capital` 占比；资金池按另一套权重重分后，虚拟现金与真实额度错位。

处理：

- 新增 `real_quota_basis`：
  - `initial_capital`（默认，兼容旧行为）；
  - `dynamic`（资金池开启时使用）：`share_i = budget_i / Σ budget`。
- `_buy_available_cash` 的真实侧额度改为按 `real_quota_basis` 计算；同时保留 `×0.98` 缓冲与会话级在途扣减。
- 若当日计划缺失/过期，回退 `initial_capital` 并记 `real_quota_fallback`，不允许静默使用 1。
- 真实侧总额度仍受 `Σ min(各组合真实额度) ≤ 真实可用` 约束，不能因为动态权重放大总额。

#### 风险三：分币舍入无最大余数法

处理：

```text
raw_i   = total × w_i
cents_i = floor(raw_i × 100)
remain  = total_cents − Σ cents_i
按 (小数余数 desc, 权重 desc, portfolio_id) 依次 +1 分
断言 Σ cents_i == total_cents
```

- 组合层、策略层都使用同一函数。
- 舍入后重新校验 `Σ budget_i ≤ pool_free`；超出则从最大额度组合回退 1 分，直到满足。
- 计划落库时同时保存 `raw` 与 `rounded`，方便对账复现。

### 8.2 对账恒等式

每个交易日至少校验以下恒等式，失败只告警不自动改账，但必须阻断新买入并升级告警：

```text
(1) Σ portfolio.cash = 会话虚拟现金合计
(2) pool_free = Σ cash − Σ open_buy_reserved − Σ fee_reserve − Σ floors ≥ 0
(3) Σ budget ≤ pool_free
(4) 每个策略：used + reserved ≤ budget
(5) Σ portfolio.total_value ≈ 真实账户.total_asset
    （容差 0.5%；连续 2 日超限升级为严重告警）
(6) Σ real_quota_i ≤ 真实账户.available_cash × 0.98
(7) 每笔成交后 cash_i ≥ 0；日终
    cash_i(收盘) = cash_i(开盘) + 卖出净额 − 买入净额 − 费用 + 资金流水
(8) 同一 code 的会话级合计市值 ≤ session_code_concentration_pct × Σ equity
```

补充：

- `(5)` 允许因 T+1 冻结、在途、估值时点产生偏差，但偏差方向和幅度要能解释；连续超限必须人工介入。
- `(7)` 是防「虚拟账本被资金池改坏」的最后一道闸；对不上时以成交流水为准重算，不以计划为准。

### 8.3 同票跨组合的持仓归因

多组合共享一个真实账户时，真实持仓是合并的，虚拟持仓是分开的。必须明确：

- **平台自己下的单**：按 `order_ref` / `strategy_id` / `portfolio_id` 归因，成交回填到对应虚拟账本。
- **外部/初始持仓**：按股票池归属；若多个组合的池重叠导致无法唯一归属，按 `(priority desc, 配置资金 desc, portfolio_id)` 兜底，并在会话启动时给出「同票归属歧义」告警。
- **同一 code 被多个组合持有**：会话级集中度按合计市值计算；单组合仍各自受 `max_single_position_pct` 约束。
- 会话创建/编辑时校验：多个组合的股票池若有重叠，前端提示「同票将按优先级归因」，并要求确认。

### 8.4 实盘生效方式

- 会话运行中修改 `capital_pool_*` / `real_quota_basis`：进入待生效队列，「下次启动生效」（与现有 `capital_pool_mode` 行为一致）。
- 计划持久化：新增 `live_capital_plans`（按 `session_id + trade_date + version` 唯一）与 `live_capital_budgets`（按组合/策略记 `budget/used/reserved`），用于重启恢复与审计。
- 重启恢复：若当日计划存在且参数版本一致，加载并保留 `used/reserved`；否则重新生成计划，但不得把已使用额度重置为 0。
- 先做**影子模式**：`capital_pool_shadow=true` 时只计算、落库、发事件，不参与 `_buy_available_cash`；对比实际成交与计划差异，稳定后再切换为强制执行。
- 实盘执行顺序：会话级熔断/日亏 → 组合风险因子 → 资金池额度 → 真实账户总闸 → 单票集中度 → 现金下限 → 容量 → 费用校验，逐层取最小。

## 9. 分阶段落地

### 阶段 0：度量与实验框架（无行为变化）

- 补齐 #4 的「请求金额 / 成交金额 / 被上限缩量」统计（现有 `order_amount_cap` 已有，补充按年、按策略聚合）。
- 增加 `target_qty`（实盘 `orig_quantity`）与 `filled_qty` 的达成率报表；回测用 `requested_qty/final_qty`。
- 增加 `capital_pool_version` 字段占位，默认 `off`。
- 风险：无；验证：指标与现有报告一致。

### 阶段 1（最小可行）：修 #4 的数学 + 单组合策略额度

改动范围：

- 新增 `max_order_pct_equity` / `max_order_adv_pct`，单笔上限 = `min(max_order_amount, pct×equity, adv×1%)`。
- `max_positions` 支持按容量配置（#4 从 10 提到 20 作为实验项，不直接改生产默认）。
- 组合内策略额度：日频、需求 + 风险因子、`λ=0.6`、上下限 5%/50%。
- 回测接入；实盘不接入。
- 默认关闭，按 run 级参数开启。

风险：

- 单笔上限放大后，容量/滑点上升；必须同时启用层 1 sqrt 容量模型与 `max_single_position_pct`。
- 需求估计若用错窗口（含当日）会引入前视，必须用单测锁死。

验证：

- 实验矩阵 A/B/C/D/E；B 必须≈A。
- 2014–2026 全区间 + 2024–2026 OOS；利用率、回撤、换手、容量触发次数。
- 单元测试：未来 bar 置换不变性、同票竞争确定性、舍入恒等式。

### 阶段 2（中等）：组合间资金池（回测）+ 实盘影子

改动范围：

- L3 会话池：多组合回测 `run_multi` 接入 `CapitalPlan`；新增 `demand_risk` 模式。
- 同票跨组合配额、会话级集中度、组合风险因子。
- 实盘影子模式：计算计划、落库、发事件，不改变下单。
- 主从：master 优先预留；slave 额度不共享钱包。

风险：

- 多组合回测结果与旧口径不可直接比较，必须并列输出。
- 影子模式可能暴露真实账户资金不足、同票归属歧义，需要先修数据。

验证：

- 多组合回测 A/B 对照；影子实盘至少 10 个交易日，计划额度与实际成交偏差 < 5%。
- 对账恒等式全绿；同票竞争事件可解释。

### 阶段 3（完整）：实盘强制执行 + 多组合会话

改动范围：

- 实盘 `_buy_available_cash` 接入额度、动态真实额度、在途扣减、最大余数法。
- 新增 `live_capital_plans` / `live_capital_budgets`；重启恢复。
- 前端：会话资金池配置、计划/执行对比、同票归属确认、告警。
- 多组合并入同一会话的校验与归因规则。

风险：

- 最高：涉及真实资金与账实一致性；必须先影子、再小资金、再全量。
- 多组合共享账户会改变单组合归因，历史业绩不可直接沿用。

验证：

- 模拟盘/小资金实盘连续 2 周，逐日对账恒等式全绿。
- 负现金事件为 0；`negative_cash_guard` 为 0；计划执行率 ≥ 95%。
- 回撤不超过组合上限；会话级熔断可正常触发。

### 推荐顺序

```text
阶段 0 → 阶段 1（先修 #4 的单笔上限与槽位）
      → 阶段 2（回测组合池 + 实盘影子）
      → 阶段 3（实盘强制）
```

理由：如果先做阶段 2/3 的资金池，单策略 #4 的利用率不会改善，容易得出「资金池没用」的错误结论；先把单笔上限和槽位修好，才能公平评估资金池的增量价值。

## 10. 验收指标

### 10.1 利用率

- 组合级：`avg_position_utilization`，按年 + 全期。
- 目标：
  - #4 类单策略：**35%–45%**（下界 #4 的 24.5%，上界 #14 的 54.4%，且必须通过容量校验）。
  - 多组合池：组合加权平均 ≥ 55%，单组合不低于 30%。
- 同时看 `empty_days_ratio`，防止「靠少数几天满仓」拉高均值。

### 10.2 目标达成率

```text
signal_fill_rate = Σ filled_qty / Σ min(requested_qty, capacity_qty)
budget_execution_rate = Σ filled_amount / Σ budget
```

- 实盘 `orig_quantity` / `filled_quantity` 已有埋点，直接用。
- 回测用 `requested_qty` / `final_qty`；被容量缩量的部分单独统计，不混入「资金不足」。
- 目标：正常流动性下 `signal_fill_rate ≥ 95%`；`budget_execution_rate` 不低于 80%。

### 10.3 回撤与风险

- 最大回撤 ≤ 8%（#4 基线 6.08%，#14 9.06%）；硬上限不超过组合 `max_drawdown`。
- 日亏触发次数不高于基线；熔断处置（half/liquidate）不增加。
- 单票集中度：组合级 ≤ 10%，会话级 ≤ 15%；超限事件为 0。
- 现金下限：日终现金 / 权益 ≥ 3%（允许因在途/T+1 短暂低于，但需有事件解释）。

### 10.4 与 #4 旧口径的对照

- 同一区间（2014-01-01 至 2026-11-19）、同一费用、同一容量模型、同一复权。
- 并列输出：总收益、年化、最大回撤、Sharpe、Calmar、年换手、`order_amount_cap` 次数、`code_quota_contention` 次数。
- 用配对日收益差做显著性检验；若收益提升主要来自少数极端日，标记为「不可复制」。
- #14 只作为「无上限不可实现」的上界参照，不作为目标函数。

### 10.5 防过拟合

- 参数只允许在训练区间（2014–2022）选择，2023–2026 作为 OOS 验证。
- `λ`、`min_share`、`max_share`、`max_order_pct_equity` 做网格时，必须报告全网格结果，不允许只展示最优。
- 任何提高利用率的改动，如果同时使 `signal_fill_rate` 下降超过 5%，视为失败。

## 11. 配置与迁移清单

### 11.1 数据模型

### 11.3 关闭开关时的等价性

- `capital_pool_enabled=false` 时：

## 12. 明确不做的事

1. **不做「主从共享钱包」**：不把 master 的现金额度直接转给 slave。
2. **不做跨会话资金池**：不同会话对应不同真实账户（tdx / iquant / goldminer），平台不做跨账户划转。
3. **不做盘中高频重分配**：默认日频；盘中只允许从「未承诺额度」借，不回收已承诺额度。
4. **不为了提高利用率而放宽容量/费用/集中度**：容量和费用必须始终生效。
5. **不把 #14 当目标**：无上限口径只用于证明上界，不作为验收标准。
6. **不在阶段 1 改实盘**：阶段 1 只改回测与参数，实盘至少到阶段 2 影子验证后再接入。

## 13. 一页结论

- **#4 的 24% 首先是一个「10 个槽位 × 50 万单笔上限」的数学问题**，不是资金池问题。先改单笔上限与槽位，才能谈组合/策略资金池。
- **主从不需要资金池**，需要的是「master 优先预留 + slave 使用剩余额度」；资金池无法消除一个 bar 的因果滞后。
- **组合间资金池只在同一会话、同一真实账户、多个组合时才有意义**；当前三个会话各一个组合，打开也不会变化。
- 推荐路线：阶段 0 度量 → 阶段 1 单笔上限/槽位/组合内额度（回测）→ 阶段 2 组合间额度（回测）+ 实盘影子 → 阶段 3 实盘强制。
- 验收以 **35%–45% 利用率、≤8% 回撤、≥95% 信号达成率、对账恒等式全绿** 为准，禁止为贴合 #14 调参。
