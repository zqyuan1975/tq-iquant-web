- 日期：2026-11-18
- 范围：J1 公司行为现金流 / J2 退市与长期停牌处置 / J7 股票池时点成分 / N1 多组合回测 + 执行仿真档位 / M1 审批队列与半自动执行 / I1 人工补单·改账·平仓入口
- 本文只写方案：不改代码、不建迁移、不提交
- 迁移基线 head：`a4b5c6d7e8f9`（`main/alembic/versions/a4b5c6d7e8f9_add_market_gate_columns.py`，已有迁移中无任何 `down_revision` 指向它）

## 0. 六条共同的硬约束

这四条先写死，后面每一条都按它推导，不再重复。

1. **手工事件表 + 有则生效、无则照旧。**
   不做自动抓取（不接交易所公告、不接 TQ 事件接口、不接第三方数据源）。事件表为空 / 开关关闭 / 该票无事件记录时，回测与实盘的执行路径、成交结果、净值曲线必须与今天**逐字一致**——不是"近似一致"。
2. **新能力一律默认关闭。**
   关闭时不新增任何分支副作用：不建 tracker、不改 `Account`/`Position`、不写 `params_snapshot` 新键（或只写显式否定值，见 §1.3），不产生新决策事件。
3. **回测与实盘共用同一套判断。**
   公司行为、退市、停牌、池成员判定的**判定内核**只有一份（`core/engine/` 下的新模块），回测与实盘各自只负责"取事件"和"落到各自账本"。不允许出现"只做在回测里"的实现。
4. **口径可冻结、可判废。**
   凡是会改变历史结果的开关，必须进 `params_snapshot`（`backtest_service.build_params_snapshot`）与增量指纹（`incremental_backtest.schema_fingerprint`）。开关一变 → 旧接缝判废、新旧记录不混比。

**已知且明确不修的边界**（写在最前面，避免验收时被当成缺陷）：

- 回测取数是前复权（`dividend_mode=front` 默认）。前复权是"加性压缩"，现金分红金额在复权价空间里**不可还原**。因此 J1 的现金分红在回测里只能用**比例**口径生效（见 §2.5），金额口径只在实盘/后复权记账腿使用。
- 实盘桥行情不复权（AGENTS 已标记的已知口径差异）在本批不处理。
- 停牌期间估值沿用"最后已知价"（`Portfolio._resolve_price` 三级兜底），不做折价模型。

## 1. 总体设计与依赖顺序

### 1.1 依赖图

```
            ┌──────────────────────────────────────────┐
            │ 阶段 0：共用内核 + 一张事件表             │
            │  corporate_actions.py / 组合级开关列       │
            └───────────────┬──────────────────────────┘
                            │
        ┌───────────────────┴───────────────┐
        ▼                                   ▼
   J1 公司行为现金流                   J7 股票池时点成分
        │（同一张表、同一内核）              │（独立，但为 N1 前置）
        ▼                                   │
   J2 退市与长期停牌                        │
        └───────────────────┬───────────────┘
                            ▼
                    N1 多组合回测 + 仿真档位
                            │（抽取 cash_allocator，实盘复用）
                            ▼
                    M1 审批队列 / 半自动
                            │（复用统一提交入口）
                            ▼
                    I1 人工补单·改账·平仓
```

**顺序理由（不是拍脑袋排的）**：

- **J1 必须先做**：它引入本批唯一一张"业务事件表"和内核对外的形状（`CorporateActionTimeline` + `apply_day`）。J2 的退市/停牌是同一张表的另外两个 `event_type`，复用同一内核；如果先做 J2，等于先写一个只服务退市的窄内核，J1 来了还要重构。
- **J7 与 J1/J2 无耦合**，但它是 **N1 的前置**：多组合回测一旦并行跑多个组合，必须能回答"这一天这只票到底在不在池里"，否则各组合的股票池口径会互相污染，结果无法解释。
- **N1 的核心不是"跑两个组合"，而是把实盘的资金审批算法抽成共用模块。** 抽取动作必须先于 M1/I1——M1 批准时要不要重算资金、I1 补单要不要走同一套额度，都依赖这个共用模块已经存在。
- **M1 必须先于 I1**：I1 的三个人工入口（补单/平仓/改账）都要复用"绕过审批队列但保留全部资金与风控闸门"的提交路径。如果 I1 先做，会写一份临时提交路径，M1 上线后再改一次，等于同一段临界区改两遍。
- **M1 的"分红自动再投资"分支**：实盘再投资要真下单，属于人工/半自动范畴。J1 的实盘再投资档因此**依赖 M1 存在**；M1 未启用时该档降级为"只记事件 + 告警"，不下单。

### 1.2 三条贯穿性设计决定

**决定 A：事件表只有一张。**
`corporate_actions` 承载 分红/送转/配股/退市/停牌 五类。理由：五类的共同锚点是"代码 + 事件日"，分成五张表会让"某票某天到底发生了什么"变成五次 union；而且 J2 的停牌处置将来要和退市共用同一段强平逻辑。

**决定 B：判定内核与账本分离。**

| 层 | 回测侧 | 实盘侧 | 共用 |
|---|---|---|---|
| 取事件 | `build_corporate_timeline(ps, start, end)` 从 DB 读 | `live_service` 组装会话时读 | 同一张表 |
| 判判定 | `corporate_actions.apply_day(portfolio, timeline, day, ...)` | 同一函数 | **同一函数** |
| 落账 | `Account.add_cash` / `Position.quantity·avg_cost` / 生成 SELL 单 | `Account.add_cash` / 柜台镜面已吸收股数变化 / 生成真实 SELL 单 | 各自的账本，内核只发"意图" |

内核返回 `AppliedAction` 列表（类型 + 代码 + 金额/股数 + 原因），由两端的薄适配层决定怎么落账。这样"回测与实盘共用判断"是结构上保证的，不依赖人工同步。

**决定 C：默认路径 = 对象为 `None`。**

所有新能力在引擎里以 `None`/`False` 默认参数注入：
`portfolio.corporate_timeline = None`、`portfolio.pool_timeline = None`、`portfolio.suspended_codes = frozenset()`、`execution_profile="legacy"`、`execution_mode="auto"`。
所有插入点第一行都是 `if xxx is None: return`，不做任何计算、不产生任何事件。这既是性能保证，也是"未启用行为不变"回归用例的抓手。

### 1.3 参数快照的统一写法

沿用 `build_params_snapshot` 现有风格：显式写"否定"值，把"功能关闭"与"旧记录缺键（口径未知）"区分开。

## 2. J1 公司行为现金流

### 2.1 目标与不做什么

**做**：

- 手工录入分红 / 送转 / 配股事件，回测与实盘按同一内核在事件日生效。
- 分红两档：`cash`（默认，现金入账）/ `reinvest`（自动再投资）。
- 配股默认放弃（只记事件、不动账、不下单）。
- 事件生效全程可审计（回测进 `decisions`，实盘进 `live_decision_events`）。

**不做**：

- 不自动抓取公告、不解析 TQ 除权数据、不推算复权因子。
- 不做红利税：`cash_per_share` 录入口径为**税后实际到账**，税前/税后由录入人负责。
- 不做配股缴款与转股（转股会引入新标的代码，超出本批范围）。
- 不改变现有复权取数（`front` 加性压缩近似照旧），不修正"前复权长区间价格趋零"这一既有已知限制。

### 2.2 数据模型与迁移

**新表 `corporate_actions`**

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | Integer PK | — | |
| `code` | String(20) | 非空 | 带后缀（`600000.SH`），与全仓口径一致 |
| `event_type` | String(16) | 非空 | `dividend` / `split` / `rights` / `delist` / `suspend` |
| `ex_date` | Date | 非空 | 除权除息日；停牌=停牌首日；退市=最后交易日 |
| `end_date` | Date | NULL | 仅 `suspend` 使用：复牌日（含当日可交易） |
| `cash_per_share` | Numeric(12,6) | NULL | 每股现金分红（元，税后）。**实盘/后复权记账腿用** |
| `cash_pct` | Numeric(10,8) | NULL | 分红占除权日前收比例（0.01=1%）。**回测复权价空间用** |
| `share_ratio` | Numeric(12,6) | NULL | 每股送转股数（0.3=10送3）；`rights` 时为配股比例 |
| `rights_price` | Numeric(12,6) | NULL | 配股价（元），仅 `rights` |
| `note` | String(200) | NULL | 备注 |
| `created_at` / `updated_at` | DateTime | `now()` | |

约束与索引：

- `UniqueConstraint("code", "event_type", "ex_date")` → 防重复录入（重复报 409）。
- `Index("ix_corporate_actions_code_date", "code", "ex_date")` → 内核按 `(code, day)` 取事件。

**`portfolio_strategies` 新增 4 列**

| 列 | 类型 | 默认 | 作用 |
|---|---|---|---|
| `corporate_actions_enabled` | Boolean | `0` | J1+J2 总开关 |
| `dividend_reinvest_enabled` | Boolean | `0` | 分红再投资档（仅 `corporate_actions_enabled=1` 时有意义） |
| `suspension_dispose_days` | Integer | `0` | 连续停牌超 N 个交易日才处置；`0`=不处置（J2） |
| `delist_force_close_enabled` | Boolean | `0` | 退市强制了结（J2，与总开关 AND） |

`downgrade()` 反向删表删列，可完整回退。

### 2.3 接口

统一 envelope（`core/api/response.py` 的 `ok()/err()`），基础路径 `/api`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/corporate-actions` | 查询：`code` / `event_type` / `start` / `end` / `page` / `page_size` |
| POST | `/api/corporate-actions` | 新增单条 |
| POST | `/api/corporate-actions/batch` | 批量新增（CSV 粘贴/数组），单事务，逐条校验后整批提交 |
| PUT | `/api/corporate-actions/{id}` | 修改 |
| DELETE | `/api/corporate-actions/{id}` | 删除 |

POST 请求：

```json
{
  "code": "600000.SH",
  "event_type": "dividend",
  "ex_date": "2024-06-20",
  "cash_per_share": 0.35,
  "cash_pct": null,
  "share_ratio": null,
  "rights_price": null,
  "end_date": null,
  "note": "2023 年度分红"
}
```

错误码：

| code | 场景 |
|---|---|
| 400 | `event_type` 不在枚举；`code` 无后缀；`ex_date` 缺失；`dividend` 两个金额字段同时为空；`split` 缺 `share_ratio`；`suspend` 的 `end_date < ex_date` |
| 404 | 修改/删除不存在的 id |
| 409 | `(code, event_type, ex_date)` 已存在 |
| 422 | 批量导入中任一条非法（返回 `data.errors[]` 带行号与原因，整批回滚） |

### 2.4 引擎改动点

**新模块 `main/core/engine/corporate_actions.py`**

```
CorporateActionEvent      # dataclass: code/event_type/ex_date/end_date/cash_*/share_ratio/rights_price
CorporateActionTimeline   # 构造时按 (code, ex_date) 建 dict；by_day(day) -> List[event]
AppliedAction             # dataclass: kind(dividend_cash|reinvest|split|delist_close|suspend_block) /
                          #            code / cash / qty_delta / price / reason
apply_day(portfolio, timeline, day, recorder, *, reinvest_enabled, price_resolver) -> List[AppliedAction]
is_suspended(timeline, code, day) -> bool
```

`apply_day` 内部按固定顺序：**送转（改股数/成本）→ 分红（现金）→ 再投资（生成 BUY 意图）→ 退市（生成 SELL 意图）→ 停牌（登记 code 集合）**。顺序不可换：先改股数再算每股分红，否则分红基数错。

**回测接入点：`core/engine/backtest_engine.py::BacktestEngine.run`**

- 位置：主循环开头、`risk_manager.enter_day(...)` **之后**、`pending_orders` 成交（step 1）**之前**。
- 守卫：`if portfolio.corporate_timeline is None: pass`；另加 `last_action_date != t.date()` 保证每日一次（混合周期多 bar/日不重复）。
- 为什么必须在成交前：当日要成交的 deferred 单如果碰上 10送3，股数必须先调整，否则成交数量按旧股数入账。
- 再投资成交：放在当日 `is_day_end` 分支（`portfolio.snapshot` 之前），用当日 close 价买入整手，不足一手的余额留现金并记 `gate=corporate_action / action=skip_lot`。生成 `TradeEvent` 入 `trades`，`signal_type` 复用 `SignalType.OPEN`，`note` 标记 `reinvest`。

**实盘接入点：`core/engine/live_engine.py`**

- `_tick_main` 的日线段（与 `_maybe_daily_bars` 同级）新增 `_maybe_apply_corporate_actions(now)`：每交易日一次、逐组合调用同一 `apply_day`。
- 落账差异（关键）：
  - **股数变动（送转）不在实盘手工改**。柜台镜面 `_refresh_available_map` → `Position.mirror_bridge` 已经会把新数量覆盖进来；`_is_share_count_change` 已识别"数量增但总成本未增"= 股本变动 → 不扣虚拟现金。实盘只记事件，避免与镜面打架。
  - **现金分红必须落虚拟现金**：`portfolio.account.add_cash(amount)`。**不走 `live_cash_flows`** —— 该表所有金额都计入 `external_net_inflow`（`live_service.cash_flow_net_inflow` 全表求和），从 `risk_equity` 里减掉；分红走那张表等于把收益当外部入金抹掉。
  - **持久化**：虚拟现金在 `recover` 时由 `live_trades` 重放，分红不在其中 → 新增 `live_corporate_actions` 应用台账（见 §2.2 迁移 4），`recover` 时按 `applied_date` 重放 `add_cash`。
  - **再投资**：`reinvest_enabled=1` 时生成一条待确认建议 —— 若 M1 已启用则入审批队列；M1 未启用则只记 `gate=corporate_action / action=notice` 告警，不下单。
  - **退市**：生成 SELL 单走 `_submit_one_order` 同一路径（全部闸门生效）；桥不可用则每日重试 + `gate=corporate_action / action=retry` 事件。
- 装配：`live_service.build_engine` 按 `gate_specs` 的做法收集**标量** `corporate_action_specs`（enabled/reinvest/dispose_days/delist）传入引擎，不持有 ORM 实例（防 `DetachedInstanceError`）。

### 2.5 参数快照与口径标记

- `params_snapshot["corporate_actions"]`：见 §1.3；`events_digest = sha1(sorted[(code, event_type, ex_date, 比例/金额)])`，用于"同参数不同事件集"的可解释性。
- 新增口径常量：`CORPORATE_ACTION_VERSION = "manual_events_v1"`（写在 `corporate_actions.py`），进快照。**内核语义一变必须改版本号**。
- **口径边界（必须写进用户文档）**：
  - `dividend_mode=front/dual` 的信号腿/记账腿都在复权价空间 → 现金分红**只认 `cash_pct`**；只有 `cash_per_share` 时记 `gate=corporate_action / action=skip_cash` WARNING 并按不处理（fail-safe，等于当前行为）。
  - `dividend_mode=back`：记账价是后复权价，同样只认 `cash_pct`。
  - 实盘：只认 `cash_per_share`（真实现金）。

### 2.6 验收标准与测试用例

`core/tests/unit/test_corporate_actions.py`（回测 + 内核）、`test_corporate_actions_live.py`（实盘落账）。

| # | 用例 | 断言 |

| 2 | 现金分红（`cash_pct=0.01`，持 1000 股，前收 10.0 → 除权日 9.9） | 现金 +100，持仓市值 -100，**组合净值不变** |
| 3 | 只有 `cash_per_share`、`dividend_mode=front` | 净值不变、现金不变、存在 `action=skip_cash` 事件 |

| 5 | 再投资 500 元、价 12.3（一手 1230） | 不成交、现金保留 500、`action=skip_lot` |

### 2.7 风险与回滚

## 3. J2 退市与长期停牌处置

### 3.1 目标与不做什么

**做**：

- 退市：按**最后可交易价**强制了结，记 `TradeEvent` + 决策事件；实盘生成真实 SELL。
- 停牌：**默认只估值不动仓**（沿用最后已知价）；只有连续停牌交易日 ≥ `suspension_dispose_days`（>0 才生效）才处置（同退市路径）。
- 停牌期间禁止新开仓/加仓（不开新仓比"继续按旧价买"安全得多）。

**不做**：

- 不做退市整理期、三板转让、退市后残值估算。
- 不做停牌期间估值折价/减值模型。
- 不改变"无成交假 bar 整行剔除"（`NO_TRADE_BAR_POLICY`）与 `pending_order_max_days=20` 的既有语义。

### 3.2 数据模型与迁移

复用 §2.2 的 `corporate_actions`：`event_type IN ('delist','suspend')`，`suspend` 用 `end_date` 表示复牌日（NULL = 至今未复牌）。**不新增表**。

`portfolio_strategies` 的 `suspension_dispose_days`（默认 0）与 `delist_force_close_enabled`（默认 0）已在迁移 1 中一并创建。

### 3.3 接口

复用 `/api/corporate-actions`（§2.3）。`suspend` 的记录在查询响应里额外返回派生字段 `is_open`（`end_date IS NULL`）与 `suspended_days`（按 `trading_days_between` 计算的交易日数），供前端列表展示。

### 3.4 引擎改动点

**内核（`corporate_actions.py`）**：

- `apply_day` 在退市事件上返回 `AppliedAction(kind="delist_close", price=最后可交易价)`。最后可交易价由调用方经 `price_resolver` 提供：回测用"事件日之前最近一根 bar 的 close"；实盘用 `_snapshot_latest_price` 或最近日线 close。
- 停牌：`is_suspended(timeline, code, day)` 判定 `ex_date <= day <= (end_date or 无穷)`；连续停牌交易日数用 `market_rules.trading_days_between(ex_date, day)`。

**回测（`backtest_engine.py`）**：

- `portfolio.suspended_codes: frozenset` 每根 bar 刷新（`apply_day` 的返回值写入）；`BacktestEngine.run` 在 step 3 调 `portfolio.on_bar` 前赋值。
- `Portfolio._signal_to_order` 的 `OPEN`/`ADD` 分支前加闸：

  ```
  if code in self.suspended_codes:
      recorder.record(gate="suspension", layer="signal_gate", action="block", ...)
      return None
  ```
  默认 `suspended_codes` 为空 frozenset → 逐字一致。
- 退市强平：在 `apply_day` 阶段直接执行（构造 SELL，按最后价成交，记账 + 记事件），不进入 `pending_orders` 队列——退市后没有下一根 bar，挂队列等于永远不成交。
- 停牌期间已有 `pending` 单：现有逻辑天然"无 bar → 不成交 → 超 20 交易日作废"；新增首次 `gate=suspension / action=hold` 事件（每单一次），让工作台能解释"为什么这单没成交"。

**实盘（`live_engine.py`）**：

- 停牌不做新开仓闸的重复实现：`_handle_bar` → `Portfolio.on_bar` 已复用同一闸（`suspended_codes` 由 `_maybe_apply_corporate_actions` 写入）。
- 退市/超期停牌强平：生成 SELL 走 `_submit_one_order`；若桥返回"停牌/非交易时间"等终态拒绝，记 `gate=corporate_action / action=rejected`，**次日重试**（不清零重试计数，人工可查）。
- 与既有 `manual_intervention` 的边界：柜台把退市股直接摘掉时，`_apply_close_counter_correction` / 镜面数量归零已会清虚拟仓并按成本回补现金；J2 的强平**优先于**该判定（先发单，发不出去才交给对账兜底）。实现上要求 `_maybe_apply_corporate_actions` 在 `_handle_bar` 的镜面刷新之前执行。

### 3.5 参数快照与口径标记

并入 §2.5 的 `corporate_actions` 区块：`suspension_dispose_days`、`delist_force_close_enabled` 直接进快照（即使为 0/false）。新增 `delist_price_basis = "last_tradeable_close_v1"` 标记，说明"最后可交易价"的取法。

## 5. N1 多组合回测 + 执行仿真档位

### 5.1 目标与不做什么

**做**：

- 一次回测跑 2..N 个组合策略，**共享同一账户资金约束**，产出成员级记录 + 聚合曲线。

- 语义**逐字保留**：按 `(bar_time, seq)` 稳定排序、80% 目标份额门槛（`_MIN_FILL_RATIO`）、`insufficient_cash/skip` 事件、单票集中度与现金留存（`_apply_allocation_caps`）、不做等比缩量。
- `LiveEngine._allocate_batch_buys` 改为 3 行委托调用（保留方法名与签名）→ 实盘行为不变的证据由既有 `test_live_engine.py` / `test_live_split_order.py` 守住。
- 回测多组合模式下按同一模块逐单审批，`available_cash` = 共享可用现金（含在途预留）。

**`backtest_engine.py` 新增 `run_multi()`**

不改现有 `run()` 的单组合路径（保持逐字一致），新增入口：

1. 入参 `portfolios: List[Portfolio]`，共用 `times` / `price_index` / `prev_close_by_day`。
2. 每根 bar：
   - 对每个 portfolio 调 `portfolio.on_bar(...)` 收集订单（各自 `inflight_risk_sells`，互不影响）。
   - 合并所有订单，按 `(portfolio_id, bar_time, strategy_id, stock_code, seq)` 排序。
   - 调 `cash_allocator.allocate_batch_buys`，`available_cash = Σ portfolio.account.cash − 在途预留`。
   - 各自成交记账（仍各用各的 `Account` 实例）。
3. 日终各 portfolio `snapshot()`，聚合 `total_value` 求和写 `aggregate.nav`。
4. 结束后逐成员写 `backtest_records`（`run_group_id` 非空），聚合指标用**合成净值曲线**重算（`Evaluator().evaluate(aggregated_snapshots)`），**不对成员指标做加权平均**。

**执行仿真档位**

`execution_profile` 是"确定性开关包"，落库时**展开成具体开关值**一并进 `params_snapshot`，保证可复现：

| profile | 展开内容 |
|---|---|
| `legacy` | 全部取组合/run 现状值（默认路径，等同于今天的 `run()`） |
| `realistic` | `price_limit_check_enabled=1`、`volume_limit_enabled=1`（`ratio=0.10`）、`adaptive_slippage_enabled=1`、`daily_close_peak_enabled=1`、`partial_fill_enabled=1`（成交量不足时按可成交部分成交，残量回队——沿用已有 `volume_cap_shrink` 语义）、`first_bar_no_fill=1`（当日首根 bar 只允许 SELL，不允许 BUY：模拟开盘撮合不确定性） |

新增的两个开关（`partial_fill_enabled`、`first_bar_no_fill`）都只在 `realistic` 下为 1；`legacy` 下为 0 且代码路径不变。

### 5.5 参数快照与口径标记

- `params_snapshot["execution_profile"]` + 展开后的每个开关值（避免"档位名同、实现变了"的不可解释）。
- `params_snapshot["multi_portfolio"] = true` + `run_group_id` + 有序 `portfolio_strategy_ids`。
- 新增口径常量 `MULTI_PORTFOLIO_VERSION = "shared_cash_allocator_v1"`，进快照——**共用分配算法的语义一变必须改版本号**。
- 增量指纹：`run_group_id` 不进指纹（它是容器 id），但 `execution_profile` 展开值进指纹。

## 6. M1 审批队列 / 半自动执行

### 6.1 目标与不做什么

**做**：

- 会话级 `execution_mode=manual`：信号产生的开仓单先入审批队列，人工批准后才真正下发到通道。
- 批准时**重新执行全部闸门**（T+1、涨跌停、资金、在途去重、槽位），不是"照抄信号时的数量"。
- 队列有 TTL、可拒绝、可批量批准、可审计（SSE + `live_decision_events`）。

**不做**：

- 不做多级审批、不做审批人权限（单用户系统）。
- 不接受"审批队列里的单可以在停止会话后继续执行"（stop 即清队列，记事件）。
- 风控卖单默认**不进队列**（见 6.4），否则等于人为延迟止损。

### 6.2 数据模型与迁移

**新表 `live_approval_queue`**

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | Integer PK | — | |
| `live_session_id` | Integer FK CASCADE | 非空 | |
| `portfolio_strategy_id` | Integer FK RESTRICT | 非空 | |
| `strategy_id` | Integer FK | 非空 | |
| `stock_code` | String(20) | 非空 | |
| `trade_type` | String(4) | 非空 | BUY / SELL |
| `price` | Numeric(10,3) | NULL | 信号价（批准时按最新价重算） |
| `quantity` | Integer | 非空 | 信号目标量 |
| `signal_type` / `signal_name` | String(15) / String(50) | NULL | |
| `bar_time` | DateTime | NULL | 信号 bar 时间 |
| `status` | String(12) | `pending` | `pending` / `approved` / `rejected` / `expired` / `dropped` |
| `reason` | String(200) | NULL | 拒绝/过期/批准时降级原因 |
| `decided_at` | DateTime | NULL | |

### 6.3 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/live/sessions/{id}/approvals?status=pending` | 列表（默认 pending，按 `created_at` 升序） |
| POST | `/api/live/sessions/{id}/approvals/{aid}/approve` | 批准单条 |
| POST | `/api/live/sessions/{id}/approvals/{aid}/reject` | 拒绝（body: `reason` 可选） |
| POST | `/api/live/sessions/{id}/approvals/approve-all` | 批量批准（按 `created_at` 顺序逐条串行，单条失败不中断其余，返回逐条结果） |

错误码：400（`reason` 超长）、404（会话/审批单不存在）、409（非 `pending` 状态重复操作 / 会话未运行 / 会话非 manual 模式）。

`approve` 响应：`data.result` ∈ `submitted` / `shrunk`（资金不足按可用缩量）/ `skipped`（闸门拦截，附 `reason`）；`data.order_id` 为新建的 `live_orders.id`。

### 6.4 引擎改动点

**`live_engine.py`**

- `_submit_one_order` 入口前插分流（在 `_book_lock` 外先判、入队时再取锁）：

  ```
  if self._is_manual_mode() and not self._approval_exempt(order):
      return self._enqueue_approval(order, portfolio)
  ```
- `_approval_exempt(order)`：风控类 SELL（`signal_type in {STOP_LOSS, TAKE_PROFIT, TRAILING_STOP}`）、`CLOSE`/`REDUCE` 一律豁免（默认）；可用 `tq_trade.approval_exempt_sells`（默认 true）放开到"所有 SELL 不审"。
- `_enqueue_approval`：**只写 `live_approval_queue`，不写 `live_orders`**（避免污染 `_pending_orders` / `_tick` 对 submitted/partial 的遍历），emit SSE `approval` 事件，返回 sentinel `None`（`LiveEngine` 已有的 `last_enqueued_order_id` 机制识别"已入队"）。
- `approve(aid)`（引擎方法，由 API 通过 `run_in_threadpool` 调用）：
  1. 取 `_book_lock`；
  2. 重算：撤销原 target，按当前可用现金 `_buy_available_cash`、当前 T+1 可用、`_check_price_limit`、`_bar_already_processed` 判重重新走一遍；
  3. 通过 → 调 `_submit_one_order(..., approval_passed=True)`（跳过入队分流）；
  4. 任一闸门拦截 → 状态 `rejected` + `reason`，记 `gate=manual_approval / action=block`。
- TTL 清扫：`_tick_main` 的 tick 段（与 `_expire_stale_orders` 同处）加 `_expire_approvals(now)`，过期 → `expired` + 事件。TTL 来自 `tq_trade.approval_ttl_seconds`（默认 900）。
- `stop()`：队列剩余单置 `dropped` 并逐条记事件（与 `split_children_lost` 同风格），**不自动执行**。
- `recover`：不重放审批队列（过期即过期），只记 `action=notice` 汇总。

**跨线程**：批准是同步阻塞（桥调用可达百 ms），必须 `run_in_threadpool`，不得在事件循环里直接调。

### 6.5 参数快照与口径标记

M1 不影响回测结果，不进 `params_snapshot`。审计留痕：

- `live_decision_events`：`gate=manual_approval`、`action=submit|reject|expire|drop`，字段含 `requested_qty`（信号量）/`final_qty`（批准后实际量）。
- 会话详情返回 `approval_pending_count`，前端铃铛角标。

`core/tests/unit/test_live_approval_queue.py`

| # | 用例 | 断言 |
|---|---|---|
| 1 | **auto 会话回归** | `execution_mode=auto` 下所有既有实盘用例逐字通过，无新表写入 |
| 2 | manual：BUY 信号 | 队列 1 条 pending、`live_orders` 无新行、SSE 收到 `approval` |
| 3 | approve | `live_orders` 出现 submitted，后续回填成交；`final_qty ≤ requested_qty` |
| 4 | approve 时资金已被别的单占用 | `result=skipped` + `reason`，不产生订单 |
| 5 | reject | 队列 rejected、无 `live_orders` 行 |

### 6.7 风险与回滚

| 风险 | 处置 |
|---|---|
| 人工未及时批准 → 错过交易时点 | TTL 默认 15 分钟 + SSE 提醒 + 前端角标；过期即明确作废，不静默 |
| 批准路径绕过闸门 → 超买/超卖 | 批准时**重算全部门槛**，且与信号提交路径共用 `_submit_one_order` |

| 停止会话后队列残留 | stop 清空并落 `dropped`；`recover` 不重放 |

**回滚**：`execution_mode` 改回 `auto` 即完全回退；新表无数据即无影响。

## 7. I1 人工补单、改账、平仓入口

### 7.1 目标与不做什么

**做**：

- 补单：人工指定代码/方向/数量/价格，走与策略单**完全相同**的提交链（闸门、去重、资金、T+1 全生效）。
- 平仓：一键卖出某票全部可用（含外部仓，按 `live_sell_scope` 现有口径）。
- 改账：修正虚拟现金/持仓与真实不一致——**只能走台账或合成成交**，不得直接改内存账本。
- 全部动作落审计表 + `live_decision_events`。

**不做**：

- 不做"直接改 `Portfolio.account.cash`"的暗改（重启即丢，且与 `risk_equity` 口径冲突）。
- 不做批量脚本/定时补单。
- 不突破 `live_sell_scope`（`platform_only` 下不代卖纯外部仓）。

### 7.4 引擎改动点

**`live_engine.py`**
