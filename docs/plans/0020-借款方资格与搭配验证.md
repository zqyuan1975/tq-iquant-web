# 借款方资格与搭配验证（0019 深化）

- 文档编号：0020
- 版本：v2（新增 §12 部署位置与操作流程、§13 借款方分类与现金管理）
- 状态：规划稿，仅设计，不含代码改动、不含迁移
- 与 0019 的关系：0019 定义了三层额度、归属、无上限预留与门控联动；本文件深化 0019 的 **「借给谁」** 与 **「搭配验证」**，并补充拼盘的部署/操作流程、借款方分类与现金出口路径，不改变 0019 的额度公式和风控口径。冲突时以 0019 的额度/风控约束为准。
- 实施基线：[0021 资金池实施任务计划](file:///d:/project/tq-iquant-web/docs/plans/0021-资金池实施任务计划.md)。本文件只定「借款方怎样才算合格、怎样搭配」；**实施范围、阶段顺序、验收与回滚以 0021 为准**。
- 结论先行：**策略/组合类借款方必须是「有冻结回测证据、且当前配置与回测快照一致」的对象；现金出口类不做策略回测，改用通道与回流判据。最多 3 个、默认 1 个；搭配必须先过硬约束、再看收益风险改善，最后用联合回测和实盘影子确认。**

## 0. 一页结论

1. **资格**：策略/组合类借款方只能是有「已完成、可冻结、可复算」回测记录的对象；回测区间至少 3 年、样本外至少 1 年、交易样本至少 100 笔，且当前参数哈希必须与回测快照一致。参数改过就失效，必须重跑。现金出口类（逆回购/货基/现金理财）不适用本节，见第 9 条与 §13。
2. **数量**：可配置多个借款方，但硬上限 3 个、默认 1 个。超过上限默认排队，不静默丢弃，也不允许「先占额度再补回测」。
3. **能否搭**：先过八条硬约束（H1–H8）——资格、共同样本外长度、单票重叠、容量参与率、现金需求重叠、容量曲线在目标规模下边际收益为正、各自回撤上限、组合级预估回撤上限。
4. **搭了是否更好**：再看收益相关性、回撤时序重叠、门控关闭重合、换手/持仓周期、资金使用互补、组合级 Sharpe/Calmar/回撤改善。硬约束失败直接拒绝；软判据失败两项以上拒绝，一项失败或三项以上警告进入「观察」。
5. **回测怎么跑**：两策略组合优先「合并组合回测」；跨组合先用「独立回测 + 资金池重放」筛选，再跑「联合多组合回测」确认。选择借款方必须 walk-forward，不能用全期业绩倒推。
6. **实盘怎么继承**：绑定关系落 `capital_pairings`，继承额度/归属/借期/召回/门控释放参数；T+1、真实可用、在途、桥延迟等不可复现因素要显式打折；先影子 10 个交易日，再小资金 2 周。
7. **界面**：不能只给「通过/不通过」。要让用户看到资格清单、八组搭配特征值、阈值、样本量、样本内外对比、预期提升、预期召回、失败条件，以及「为什么这组值得/不值得开」。
8. **部署与流程**：入口放在回测管理（新增「新建拼盘」向导），组合页只保留主从语义，实盘页负责绑定与继承；拼盘不是新的回测结果口径，详见 §12。
9. **借款方分两类**：`borrower_type=strategy/portfolio` 用 E1–E12；`borrower_type=cash_outlet`（逆回购/货基/现金理财）不做策略回测，改用通道、收益率、流动性、限额、回流确定性判据 C1–C8，详见 §13。**当前「现金管理增强」仍是纯占位，只记决策事件、不下单**。

## 1. 借款方资格：策略/组合必须是「已完成回测的对象」

> 现金出口（`borrower_type=cash_outlet`）不属于本节，见 §13。本节及 §1.4 的 E1–E12、12 种拒绝码只适用于策略/组合。

### 1.1 借款单元

| 层级 | 借款方单位 | 必须具备的回测 |
|---|---|---|
| L2 组合内（同组合多策略） | 策略 | 该策略自己的已完成回测；若它依赖主从，必须包含 master 的联合回测 |
| L3 会话内（多组合） | 组合 | 该组合级的已完成回测（组合内所有策略一起跑），不能只用单个策略成绩代替 |
| 自定义 A→B | 策略或组合 | 两边各自的已完成回测 + 至少一次联合回测/重放 |
| 现金出口（非策略） | 通道 / 产品 | **不做策略回测**；用通道验证、收益率曲线、结算规则判定，见 §13.2 的 C1–C8 |

**不接受**：只建了策略、没有回测记录；只有实盘记录、没有可复现回测；回测还在 running；用别的策略的回测结果冒充；空壳组合（无策略、无股票池、无初始资金）。

**分类前提**：上表前三行只适用于 `borrower_type=strategy/portfolio`。`borrower_type=cash_outlet` 的借款方没有 alpha、没有信号、没有回测收益，套用「已完成回测 + 指标冻结」是概念错误；它只回答「钱放进去能不能按约定时点和可验证收益率回来」。

### 1.2 资格判据（全部满足才通过）

> E1–E12 只适用于策略/组合类借款方。`cash_outlet` 不适用本节，改用 §13.2 的 C1–C8；把回测资格套到现金出口上会直接误杀（它本来就没有策略回测）。

| 编号 | 判据 | 建议阈值 | 说明 |
|---|---|---|---|
| E1 | 回测记录状态 | `completed` | running/失败/取消都不算 |
| E2 | 评估指标已冻结 | 有 `evaluation_id` 或不可变评估快照 | 防止事后改指标 |
| E3 | 参数快照一致 | `params_hash` = 当前策略/组合配置哈希 | 改了参数就失效，必须重跑 |
| E4 | 回测区间长度 | ≥ 756 个交易日（约 3 年） | 覆盖至少一轮完整牛熊 |
| E5 | 样本外长度 | ≥ 252 个交易日（约 1 年） | 训练/验证分开，OOS 不能参与选参 |
| E6 | 交易样本 | ≥ 100 笔成交，且有持仓交易日 ≥ 250 | 低频策略可把 100 笔降到 30 笔，但需显式配置 |
| E7 | 门控周期覆盖 | 门控开/关各 ≥ 60 个交易日 | 没有空头段的策略无法评估门控释放 |
| E8 | 组合绑定 | `portfolio_id` 存在、`initial_capital > 0`、股票池非空 | 空壳组合直接拒绝 |
| E9 | 容量数据 | 有 20 日 ADV 与容量参数 | L3 必须；L2 缺失可降级但限制出借额 |
| E10 | 风控配置 | `max_drawdown` / `daily_loss_limit` 已配置 | 缺失时用默认值并标记降级 |
| E11 | 数据质量 | 缺失 bar < 2%、无重复日、无负价 | 数据脏的策略不能借 |
| E12 | 决策时点 | 回测完成时间早于搭配决策日 | 不能用「未来才跑出来的好成绩」选人 |

### 1.3 冻结与失效

- 资格不是一次性认证：每次生成资金计划前重新校验 `params_hash`。
- 以下任一变化 → 资格立即失效，状态置 `STALE`，停止新增出借，存量 LoanLot 只回收不续期：
  - 策略参数（`max_positions`、`single_open_ratio`、`max_order_amount`、`capital_ratio`、门控配置等）变化；
  - 股票池变化；
  - 组合 `initial_capital` / `equity_cap` / `target_utilization` 变化；
  - 回测引擎版本或容量模型版本变化；
  - 实盘账户/执行模式变化（进入实盘阶段后）。
- 失效不是「重新算一下就行」：必须重跑回测并重新通过资格，才恢复。

### 1.4 拒绝原因（必须对用户可见）

| 代码 | 含义 | 用户提示 |
|---|---|---|
| `NO_BACKTEST` | 没有回测记录 | 「该策略还没有完成回测，不能作为借款方」 |
| `BACKTEST_RUNNING` | 回测未完成 | 「回测仍在运行，完成后自动重新评估」 |
| `PARAMS_STALE` | 参数与回测快照不一致 | 「参数已修改，请重跑回测」 |
| `HISTORY_TOO_SHORT` | 区间不足 3 年 | 「历史不足 756 个交易日」 |
| `OOS_MISSING` | 无样本外 | 「缺少至少 1 年样本外区间」 |
| `TRADES_TOO_FEW` | 交易样本不足 | 「成交样本少于 100 笔」 |
| `GATE_COVERAGE_LOW` | 门控开/关覆盖不足 | 「缺少空头/多头完整段」 |
| `NOT_BOUND` | 未绑定组合/资金/股票池 | 「组合未配置完整」 |
| `CAPACITY_MISSING` | 无容量数据 | 「缺少 ADV 数据，不能做会话级出借」 |
| `DATA_QUALITY` | 数据缺失/重复/异常 | 「回测数据质量不达标」 |
| `EVAL_NOT_FROZEN` | 指标未冻结 | 「评估结果不是不可变快照」 |
| `DECISION_TIME_LEAK` | 回测完成时间晚于决策日 | 「不能用未来回测结果选借款方」 |

现金出口的拒绝码是另一套（`CHANNEL_UNSUPPORTED`、`YIELD_DATA_MISSING`、`LIQUIDITY_MISMATCH`、`LIMIT_TOO_SMALL`、`REDEMPTION_RESTRICTED`、`RISK_LEVEL_HIGH`、`SETTLEMENT_UNCERTAIN`、`OUTLET_NOT_VERIFIED`），见 §13.2。

### 1.5 资格与主从

- slave 作为借款方时，必须有 **master+slave 联合回测**，不能只看 slave 单独回测；因为 slave 的成交依赖 master 持仓。
- master 作为借款方时，必须证明「借出后仍能覆盖自身开仓 + slave 授权所需的最低预留」，否则资格不通过（master 优先预留的算法见 0018 §5.4，0019 阶段 B 继续沿用）。

## 2. 数量约束：默认 1 个、硬上限 3 个

### 2.1 为什么设上限

| 原因 | 说明 |
|---|---|
| 资金碎片化 | 每多一个借款方，池内可借额被切得更碎；低于最小出借单位后，调度成本大于收益 |
| 调度复杂度 | n 个借款方的两两搭配检查是 `n(n-1)/2`；1/2/3/4/5 个分别是 0/1/3/6/10 组 |
| 同票冲突概率 | 单票冲突概率约 `1-(1-p)^(n-1)`；p=10% 时，2 个约 10%，3 个约 19%，5 个约 34% |
| 召回协调 | 多个借款方同时被召回时，现金回流顺序、优先级和 shortfall 处理会迅速复杂化 |
| 可解释性 | 超过 3 个后，用户很难判断「这笔钱到底帮了谁」，UI 也难解释 |

因此：**`max_borrowers` 默认 1，硬上限 3；配置超过 3 直接校验失败，不允许落库。**

### 2.2 数量与额度分配

| 活跃借款方数 | 单个借款方最大占比 | 最小出借占比 | 说明 |
|---:|---:|---:|---|
| 1 | 100% 可借额 | 5% | 默认，最易解释 |
| 2 | 60% | 5% | 保留竞争与召回缓冲 |
| 3 | 45% | 5% | 硬上限，必须两两通过硬约束 |

补充：

- 单笔出借低于 `max(一手市值, 5% × cash)` 不登记，避免碎片化。
- 同一 `code` 的借款方合计不得超过该票容量；同票冲突按 0019 §5 的 Step 8 同票配额处理（分配算法见 0018 §5.3）。
- 新借款方加入时，必须与所有现有借款方两两通过硬约束；任一不通过则拒绝。
- **现金出口计入同一个 `max_borrowers` 上限**：不允许「3 个策略 + 1 个现金出口」绕过；否则资金碎片化与解释成本仍会失控。若用户只想在闲置时放逆回购，正确做法是把出口设成唯一借款方，或用 0019 的 `cash_management` 归属策略（阶段 F 后才可用）。
- 上表的 100%/60%/45% 是策略/组合类上限；现金出口另受 `cash_outlet_max_share`（默认 50%）约束，两者取小。出口的目的不是占满额度，而是把「确定用不到的闲钱」放到可回流的地方。

### 2.3 超过上限：排队还是拒绝

三选一，默认 `queue`：

| 策略 | 行为 | 适用 |
|---|---|---|
| `queue`（默认） | 进入等待队列，按搭配评分排序；有借款方归还/退出时递补；队列 TTL 20 个交易日 | 大多数场景 |
| `reject` | 直接拒绝，`BORROWER_LIMIT_REACHED` | 强合规、强解释场景 |
| `manual` | 仅展示候选，由用户手动启用 | 自定义搭配 |

排队规则：

- 等待期间不预分配额度、不生成 LoanLot、不冻结资金。
- 每天重新校验资格；参数变化或资格失效自动出队。
- 队列顺序：搭配评分 desc → 预期利用率提升 desc → `strategy_id` 兜底。
- 用户界面显示「当前排队第 N 位、预计释放条件、已等待天数」。

## 3. 搭配评估：看哪些特征

### 3.1 两类判据

- **能不能搭（硬约束）**：不满足就不能建立借贷关系，避免结构性冲突。
- **搭了是否更好（软判据）**：满足硬约束后，再看是否真的改善收益风险；不改善就不开。

所有特征在**共同交易日**上计算，且使用**样本外**区间；样本内只用于展示，不参与通过/不通过。**现金出口不参与这些特征**：它没有收益序列之外的信号，也不存在同票与门控重合，改用 §13.2 的 C1–C8。

### 3.2 硬约束（任一失败 → 不能搭）

> H1–H8 只适用于两个策略/组合之间的搭配。借款方是 `cash_outlet` 时，相关性、同票重叠、门控重合等特征不适用，改用 §13.2 的 C1–C8；不要为了「走同一套流程」给现金出口硬造相关性。

| 编号 | 判据 | 阈值 | 失败处理 |
|---|---|---|---|
| H1 | 双方资格通过 | 见第 1 节 | 拒绝 `BORROWER_INELIGIBLE` |
| H2 | 共同样本外长度 | ≥ 252 个交易日 | 拒绝 `COMMON_OOS_TOO_SHORT` |
| H3 | 单票重叠率 | 持仓加权重叠 ≤ 0.60 | 拒绝 `CODE_OVERLAP_HIGH` |
| H4 | 容量参与率 | 各自 ADV 参与率 ≤ 1%；同票合计 ≤ 2% | 拒绝 `CAPACITY_CONFLICT` |
| H5 | 现金需求同日重叠 | ≤ 0.80 | 拒绝 `CASH_TIMING_CONFLICT` |
| H6 | 容量曲线边际收益 | 在目标规模（1× 和 2×）下边际收益 > 0 | 拒绝 `CAPACITY_NEGATIVE` |
| H7 | 各自最大回撤 | 不超过组合/会话回撤上限 | 拒绝 `RISK_LIMIT_BREACH` |
| H8 | 组合级预估最大回撤 | 不超过上限，且不高于两者较优者的 +1pp | 拒绝 `COMBINED_DD_BREACH` |

### 3.3 软判据（决定「值不值得」）

| 特征 | 定义 / 数据来源 | 通过 | 警告 | 不通过 |
|---|---|---|---|---|
| 收益时序相关性 | 共同 OOS 日收益 Spearman；另看 60 日滚动 p90 | ≤ 0.30 | 0.30–0.70 | > 0.70 |
| 回撤时序重叠 | 双方同时处于回撤 > 3% 的交易日 Jaccard | ≤ 0.30 | 0.30–0.50 | > 0.50 |
| 各自最大回撤 | 回测日快照计算 | ≤ 上限的 75% | 75%–100% | > 上限 |
| 回撤持续期 | 峰值到恢复的交易日数，取 p90 | ≤ 120 日 | 120–180 日 | > 180 日 |
| 持仓周期 | 成交配对后的中位持有天数 | 双方差异 ≥ 2 倍（互补） | 1.2–2 倍 | 接近一致 |
| 年换手率 | 评估指标 | 双方均 ≤ 45× | 45–60× | > 60× |
| 容量占用重叠 | 同票同日 `min(参与率_i, 参与率_j)` 加权 | ≤ 0.10 | 0.10–0.25 | > 0.25 |
| 门控关闭重合 | 双方门控关闭日的 Jaccard（仅对受门控策略） | ≤ 0.50 | 0.50–0.70 | > 0.70 |
| 同票重叠率（信号） | 同日同票 OPEN 信号的重叠比例 | ≤ 0.30 | 0.30–0.60 | > 0.60 |
| 同票抢单概率 | 同日同票合计需求 / 该票容量，历史分布 p90 | ≤ 0.50 | 0.50–0.80 | > 0.80 |
| 资金使用互补 | 一方现金需求 >5% 权益、另一方 <1% 的交易日占比 | ≥ 0.30 | 0.10–0.30 | < 0.10 |
| 容量曲线斜率 | 1× → 2× → 5× 规模下的年化收益衰减 | 2× 衰减 ≤ 20% | 20%–40% | > 40% 或转负 |
| 组合 Sharpe 改善 | 动态池 vs 较优单策略 | ≥ +0.10 | 0 ～ +0.10 | < 0 |
| 组合 Calmar 改善 | 同上 | ≥ +0.10 | 0 ～ +0.10 | < 0 |
| 组合收益 | 动态池年化 vs 较优单策略 | ≥ −2pp | −2 ～ −5pp | < −5pp |
| 利用率提升 | 动态池 vs 静态等额 | ≥ +10pp | 0 ～ +10pp | < 0 |
| 预期召回频率 | 回测中的年化召回次数 | ≤ 12 次/年 | 12–24 次/年 | > 24 次/年 |
| 预期召回 shortfall | shortfall 金额 / 出借总额 | ≤ 2% | 2%–5% | > 5% |

### 3.4 判定规则

```text
1. 任一硬约束失败 → NO_GO
2. 软判据「不通过」≥ 2 项 → NO_GO
3. 软判据「不通过」= 1 项，或「警告」≥ 3 项 → WATCH（只观察，不实盘）
4. 其余 → GO（仍需联合回测确认）
```

**不采用单一加权总分做最终决定**。总分只用于候选排序；通过/不通过必须能追溯到具体判据，避免「综合分 82 分所以可以开」这种不可解释的结论。

### 3.5 特征数据来源

| 特征 | 来源 |
|---|---|
| 日收益、回撤、现金/持仓 | 回测日快照（`backtest_daily_snapshots`），按共同交易日对齐 |
| 换手、最大回撤、Calmar | 回测评估（`backtest_evaluations`） |
| 持仓周期、同票重叠 | 成交流水（`backtest_trades`）与持仓快照 |
| 门控关闭时段 | 日快照中的 `gate_state` / 门控快照表 |
| 容量、ADV 参与率 | 层 1 容量预算与 20 日 ADV；必要时做 1×/2×/5× 规模回测 |
| 资金使用时段 | 日快照 `cash` 变化 + 当日买入请求金额 |
| 召回/利用率 | 资金池重放或联合回测的 `capital_loan_lots` / 计划事件 |

### 3.6 对「同票」和「门控」的特别说明

- **同票重叠不是绝对禁止**：如果两边都对同一只票有信号，但合计需求远低于容量、且入场时点错开，可以接受；所以设 0.60 硬上限 + 抢单概率软判据。
- **门控关闭重合不是绝对坏事**：如果一方是趋势策略、另一方不受门控影响（`market_gate_mode=off`），关闭期正好互补；只有双方都受门控且关闭日高度重合时，才判为「不能互补」。
- **相关性低不等于互补**：两个都长期空仓的策略相关性也低，但没有资金需求；必须同时看「资金使用互补」和「利用率提升」。

## 4. 搭配后的回测怎么跑

### 4.1 三种方案与取舍

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 合并组合回测 | 选定一个**已包含主与搭配对象两个策略**的组合，共用现金/容量/门控，跑一个组合级回测（两个策略分属不同组合时不能走 L2） | 最接近 L2 真实语义；能捕捉同票、容量、现金竞争 | 需要先在组合页完成装配；策略归因要额外拆 | L2 同组合，最终确认 |
| B. 独立回测 + 资金池重放 | 各自先独立跑，再把每日需求/现金按资金池规则做重放 | 快，适合批量筛选 | 成交反馈、滑点、部分成交被简化；不能完全代表联合结果 | L3 初筛 |
| C. 混合（推荐） | B 筛候选 → 联合重放（含容量/借贷/召回/门控）→ A 或联合多组合回测确认 | 兼顾效率与真实性 | 流程长，需要版本管理 | L3 最终确认 |

**推荐**：

- L2（同组合）：直接 A，合并组合回测；另出「不借贷」的静态分配对照。
- L3（跨组合）：B 初筛 → C 联合重放 → 联合多组合回测确认；不能只用 B 的结果上线。
- 任何方案都必须记录 `capital_pool_version` 与 `fields_hash`，否则结果不可比。

### 4.2 资金池在回测中的建模

```text
每日首 bar：
  1. 计算各组合/策略的 entitlement、OwnNeed、Lendable
  2. 门控 CLOSED → 需求=0，闲置额度进入 PENDING_RELEASE
  3. 汇总 PoolFree；按归属 scope 选择借款方
  4. 生成 LoanLot 与 budget
  5. 当日下单时取 min(策略额度, 现金, 容量, 单票上限, 整手)
  6. 成交回填 used；未成交保留 reserved；撤单释放
  7. 门控 OPEN → 发起 recall；借款人冻结新买入，按成交/现金归还
  8. 日终写归属表与对账恒等式
```

- 回测里的借贷是虚拟的：不改变组合 `Account` 的现金归属，只改变「谁能花」；归还时释放额度。
- 借款人的成交仍按现有回测撮合/容量模型执行，不能因为「借到额度」就绕过容量。
- 召回不能假设瞬间到账：按借款人卖出成交或下一 bar 可用现金回填，记录 `recall_shortfall`。
- 同票配额与容量共享必须在重放中显式建模，否则会高估搭配收益。

### 4.3 无前视与防拟合

1. **Walk-forward 选人**：每个季度末，只用截至该日的数据计算资格与搭配评分，决定下一季度借款方；下一季度只做 OOS 评估。不得用全期表现挑人。
2. **参数冻结**：搭配阈值（相关性、重叠率、上限）在回测前预注册，不能边跑边调。
3. **候选全集**：把当时可用的所有合格对象都纳入候选，不能只展示最终赢家。
4. **多重试验记录**：报告尝试过的搭配数量；如果试了很多组，OOS 结果要打折或做 Bonferroni 校正。
5. **门控右移**：门控状态只用严格早于当日的状态；需求用上一交易日前 N 日；ADV 用前 20 日；容量用当前 bar 截至当下的累计量。
6. **禁止未来信息**：不得用当日收盘后的信号决定当日开盘额度；不得用未来回测记录做当日资格判断。
7. **样本内外分栏**：报告必须同时给出 IS 与 OOS；只给全期合并指标视为不合格。

### 4.4 对照基线

| 基线 | 说明 | 用途 |
|---|---|---|
| A 单独 | 借款方 A 单独跑 | 判断搭配是否伤害 A |
| B 单独 | 借款方 B 单独跑 | 判断搭配是否伤害 B |
| 静态等额 | 50/50 固定资金，不借贷 | 证明动态池的增量 |
| 静态配置比例 | 按 `capital_ratio` 固定切分 | 对照 0019 之前的静态切分 |
| 动态资金池 | 本方案 | 候选 |
| #4 旧口径 | 单策略 50 万上限 | 单策略基线 |
| #14 无上限 | 不可实现上界 | 仅参照，不作为目标 |

### 4.5 结果不一致时以什么为准

优先级从高到低：

1. **资格与硬约束**：不通过就是不通过，不能被高收益覆盖。
2. **联合回测（A 或联合多组合）**：涉及同票、容量、现金竞争时，以联合结果为准；独立重放只用于筛选。
3. **OOS 结果**：OOS 不通过，IS 再好也拒绝。
4. **较优单策略基线**：如果动态池的 Sharpe/Calmar 低于较优单策略，或最大回撤更差超过 1pp，拒绝搭配。
5. **实盘影子**：影子偏差 > 5%，不进入实盘强制执行。

明确规则：

- 重放与联合回测关键指标差异 > 20%（利用率、年化、回撤任一）→ 视为建模错误，重跑联合回测，不能挑好看的那个。
- 搭配后借款方 A 的收益/回撤明显变差（超过预设容忍）→ 即使组合整体更好，也要拒绝或降低 A 的出借比例；不能牺牲出借人。
- 任何手动放行必须记录理由、审批人和有效期；默认不允许覆盖硬约束。

## 5. 搭配后如何被实盘继承

### 5.1 绑定关系

新增 `capital_pairings`：

```text
id, session_id, scope,
lender_type, lender_id,
borrower_type, borrower_id,  # strategy / portfolio / cash_outlet
status,                    # ACTIVE / WATCH / SUSPENDED / RETIRED
max_share,                 # 该借款方最大占比
loan_term_days, recall_notice_days, release_delay_days,
eligibility_backtest_id, evaluation_id, params_hash,
outlet_verification_id,    # 仅 cash_outlet：通道验证记录，替代 eligibility_backtest_id
pairing_version,           # 与 0019 的 fields_hash 对齐
effective_from, effective_to,
created_by, created_at
```

- 一个会话内活跃借款方 ≤ 3；同一借款方不能重复绑定。
- `cash_outlet` 不要求 `eligibility_backtest_id`，但必须有 `outlet_verification_id`；绑定有效期不得超过通道验证的有效期。
- 本表只存「边」；拼盘整体（成员、版本、证据、生命周期）落在 `capital_pairing_plans`，见 §12.3。
- 绑定前必须重新校验资格与硬约束；任何一项失效 → 拒绝创建。
- 绑定不是永久：`effective_to` 默认 1 年，到期重新评估。

### 5.2 继承矩阵

| 配置 | 是否继承 | 说明 |
|---|---|---|
| `pool_scope` / `ownership_policy` | 继承 | 来自会话配置 |
| `max_borrowers` / 队列策略 | 继承 | 会话级 |
| `loan_term_days` / `recall_notice_days` / `release_delay_days` | 继承 | 会话级 |
| `no_cap_reserve_policy` | 继承 | 策略/组合级 |
| 门控 `gate_hysteresis_days` | 继承 | 会话级 |
| 借款方 `max_share` | 继承 | 绑定级，可单独调低 |
| 资格回测记录 / `params_hash` | **重新校验** | 参数变化即失效 |
| 账户绑定、执行模式 | **重新校验** | 实盘阶段必须 |
| 容量/ADV | **重新计算** | 用实盘最新数据 |
| 同票重叠 | **重新计算** | 实盘持仓可能与回测不同 |

### 5.3 回测有效但实盘无法完全复现的因素

| 因素 | 回测假设 | 实盘现实 | 影响 |
|---|---|---|---|
| T+1 | 卖出资金可当日再买 | 可用资金/冻结受柜台规则影响 | 召回速度、利用率 |
| 真实可用资金 | 虚拟现金即全部可用 | 柜台可用 < 总资产 | 借款额度可能被高估 |
| 在途/未成交 | 成交即回填 | 有挂单、部分成交、撤单延迟 | 负现金、额度重复占用 |
| 成交回补 | 撮合模型 | 桥接延迟、回报顺序 | 账实偏差 |
| 滑点/费用 | 模型估算 | 实际冲击、印花税/佣金 | 收益高估 |
| 涨跌停/停牌 | 模型处理 | 无法成交/延迟 | 召回 shortfall |
| 外部持仓 | 通常无 | 真实账户可能已有持仓 | 归因与集中度 |

处理要求：

- 实盘影子期用真实成交反推 `live_haircut`：至少校准利用率、滑点、成交率三项。
- 回测收益不能直接作为实盘预期；实盘看板必须显示「回测 → 影子 → 实盘」三列。
- 上述因素导致无法满足硬约束（如容量参与率超限）时，自动降级或暂停搭配，不靠人工解释。

### 5.4 继承后的一致性验证

| 检查 | 方法 | 通过标准 |
|---|---|---|
| 计划一致性 | 影子计划 vs 回测重放同一天额度 | 偏差 < 5% |
| 门控一致性 | 实盘门控状态 vs 回测状态 | 100% 一致 |
| 成交率 | `filled / min(requested, capacity)` | ≥ 95% |
| 滑点 | 实际成交价 vs 回测模型 | 在模型 ±20% 内 |
| 对账 | 0019 的恒等式 (1)–(10) | 全绿 |
| 负现金 | `negative_cash_guard` | 0 |
| 召回演练 | 人工触发召回 | 1 个交易日内完成，shortfall 可解释 |

先影子 10 个交易日；通过后小资金 2 周；再全量。任何一步不通过，停在当前阶段。

### 5.5 实盘运行后的健康指标与解除条件

搭配状态生命周期：

```text
ACTIVE → WATCH（预警）→ SUSPENDED（停止新增出借）→ RETIRED（解除）
```

| 指标 | 正常 | WATCH | SUSPENDED / 解除 |
|---|---|---|---|
| 20/60 日收益相关性 | ≤ 0.5 | 0.5–0.7 | > 0.8 连续 5 个交易日 |
| 组合最大回撤 | ≤ 回测值 + 2pp | +2 ～ +3pp | > 上限，或 > 回测值 + 3pp |
| ADV 参与率 | ≤ 1% | 1%–1.5% | > 1.5% 连续 5 日 |
| 同票抢单事件 | ≤ 5%/月 | 5%–10%/月 | > 10%/月连续 2 月 |
| 召回频率 | ≤ 12 次/年 | 12–24 次/年 | > 24 次/年 |
| 召回 shortfall | ≤ 2% | 2%–5% | > 5% 或单季 > 2 次 |
| 借款人成交率 | ≥ 95% | 90%–95% | < 90% 连续 5 日 |
| 出借人恢复期成交率 | ≥ 90% | 80%–90% | < 80% 连续 5 日 |
| 资格 `params_hash` | 一致 | — | 不一致立即 SUSPENDED |
| 对账恒等式 | 全绿 | 单日告警 | 连续 2 日失败 |

解除规则：

- `SUSPENDED` 只停止新增出借，不强制平仓；存量 LoanLot 按到期/召回自然回收。
- 恢复需要连续 5 个交易日指标回到正常，且用户确认。
- `RETIRED` 为永久解除，保留历史账本；重新开启按新绑定处理。
- 自动暂停优先于人工解释；任何人工恢复必须记录理由与有效期。

### 5.6 「搭配按预期工作」的判定

同时满足：

1. 组合利用率达到回测预期的 80% 以上；
2. 组合 Sharpe/Calmar 不低于回测 OOS 的 80%；
3. 相关性、回撤、容量、召回、成交率均在正常区间；
4. 出借人自身策略没有被明显伤害（收益/回撤在容忍内）；
5. 对账全绿、无负现金、无未解释 shortfall。

任一条持续不满足 → 进入 WATCH/SUSPENDED，而不是继续「观察看看」。

## 6. 界面上让用户看到什么

### 6.1 候选列表

每个候选显示：

- 资格徽章：通过 / 不通过 / 降级（含具体原因代码）；
- 回测区间、样本内外长度、成交笔数；
- 当前是否已绑定其他会话；
- 搭配评分与排名（仅排序，不等于通过）。

### 6.2 搭配详情页（核心）

必须包含以下区块，不能只给一个总分：

1. **资格清单**：E1–E12 逐项通过/失败与原因。
2. **硬约束**：H1–H8，失败项标红并说明「为什么不能搭」。
3. **特征面板**：第 3.3 节全部软判据的实际值、阈值区间、样本量、样本内外对比（按八组归类展示：时序相关性、回撤、周期与换手、容量、门控、同票、资金时段、规模敏感度）。
4. **收益风险对比图**：
   - A 单独、B 单独、静态 50/50、动态池四条净值/回撤曲线；
   - 利用率曲线；
   - 召回次数与 shortfall 标注。
5. **解释卡**：
   - 三条最强支持理由（例：收益相关性 0.18、现金使用互补 42%、门控关闭重合 21%）；
   - 三条最大风险（例：同票重叠 0.52、容量斜率 2× 衰减 28%、预期召回 18 次/年）；
   - 每条都带数据来源与样本区间。
6. **决策卡**：
   - 结论：GO / WATCH / NO_GO；
   - 预期利用率提升、预期 Sharpe/Calmar 变化、预期最大回撤；
   - 预期召回频率与 shortfall；
   - 失败条件（什么情况下会自动暂停）；
   - 需要用户确认的选项（最多 3 个借款方、排队策略、是否允许自定义搭配）。
7. **样本内外分栏**：IS 与 OOS 分开显示，禁止只展示全期最优。
8. **版本与冻结信息**：回测记录 ID、`evaluation_id`、`params_hash`、`capital_pool_version`；参数变化后显示「结果已过期」。

### 6.3 运行后看板

- 当前 ACTIVE/WATCH/SUSPENDED 列表；
- 每个借款方的额度、已用、借出、召回中；
- 滚动相关性、回撤、ADV 参与率、同票冲突、召回次数；
- 最近一次对账结果与告警；
- 一键「停止新增出借」（不强制平仓）与「解除绑定」。

### 6.4 不做的 UI 设计

- 不显示单一「综合评分 82 分」作为结论；
- 不用绿色勾选掩盖样本不足或 OOS 缺失；
- 不允许在未查看硬约束失败原因的情况下强制开启（除非管理员二次确认并留痕）。

## 8. 验收指标

### 8.1 资格与数量

- 资格判据单测覆盖 12 种拒绝码；
- 参数改动后 100% 失效，不允许继续借；
- 默认 1 个、硬上限 3 个；第 4 个必须排队/拒绝，且有可见原因；
- 队列 TTL 生效，过期自动出队。

### 8.2 搭配质量

- 硬约束误放行 = 0（用合成反例验证）；
- 软判据结论可追溯到具体特征；
- OOS 与 IS 分栏，禁止只展示全期；
- 借款方 A/B 自身指标不被搭配显著伤害（收益 −2pp / 回撤 +1pp 容忍内）。

### 8.3 回测有效性

- 联合回测与独立重放关键指标差异 ≤ 20%；超过则必须重跑并解释；
- 动态池 vs 静态等额：利用率提升 ≥ 10pp，Sharpe/Calmar 不下降；
- 召回次数与 shortfall 在阈值内；
- 未来数据置换测试通过（打乱未来 bar 不影响当日计划）。

### 8.4 实盘继承

- 影子 10 日计划偏差 < 5%，门控状态 100% 一致；
- 小资金 2 周对账全绿、负现金 0；
- 自动暂停演练：构造相关性升高/容量超限，5 个交易日内进入 SUSPENDED；
- 解除演练：指标恢复后连续 5 日正常才允许恢复。

1. 不允许没有完成回测的策略/组合成为借款方。

## 12. 部署位置与操作流程（拼盘）

### 12.0 三个词先对齐

| 词 | 含义 | 不是什么 |
|---|---|---|
| **主出资方** | 出借额度的一方。L2 是策略，L3 是组合 | 不是组合页里 `role=master` 的主策略 |
| **搭配对象** | 使用额度的一方，`borrower_type=strategy / portfolio / cash_outlet` | 不一定是「另一个策略」，也可能是现金出口 |
| **拼盘** | 一套搭配方案（`capital_pairing_plans`）+ 它的回测证据 | 不是新的回测结果口径，也不等于一条 `backtest_records` |

`master/slave` 是**信号门禁**：slave 必须等 master 持仓后才能开仓；拼盘是**资金搭配**：谁把闲置额度借给谁。两者可以同时存在，但 UI 文案必须区分，禁止把主出资方写成「主策略」。

### 12.1 部署在哪里

| 页面 | 现有能力（已存在） | 本期新增（规划，不代表现在可点） | 职责 | 阶段 |
|---|---|---|---|---|
| **回测管理** `/backtest` | 「+ 发起回测」（单组合）、「对比所选 (n)」、「信号回放」、记录列表的 查看/取消/删除、回测详情 | 页头「+ 新建拼盘」向导；记录列表的「拼盘」标签/折叠；拼盘详情（方案 + 证据 + 基线）；「重新评估 / 重跑联合回测 / 绑定实盘」 | 挑主、挑搭配、资格校验、搭配评估、联合回测、生成拼盘 | B 入口（仅 L2）；E 完整 |
| **组合策略** `/portfolios` | 组合 CRUD；策略 CRUD；`role=master/slave`、主策略、卖出模式；`capital_ratio`、槽位、单笔上限等 | 不做拼盘向导。只加一个只读徽标「被拼盘 P-xxx 引用」，点击跳到回测管理的拼盘详情 | 定义策略、组合与主从关系；不承担资金搭配 | 不变 |
| **实盘交易** `/live` | 「+ 新建实盘」多选组合；编辑会话；「理论 vs 实盘」绑定**单条**回测记录；`capital_pool_mode` 选择 | 新建/编辑会话增加「拼盘」选择；会话页拼盘卡片；理论 vs 实盘支持**运行组/拼盘**绑定；健康看板；暂停/退役 | 绑定拼盘、继承参数、影子验证、实盘监控 | F 绑定；G 强制执行 |

补充事实，避免文档让人误以为现在就能用：

- 后端已有 `POST /api/backtest/run-multi`、运行组列表/详情接口，但前端**没有 API 客户端、没有入口**；普通回测列表也不会显示 `run_group_id`，成员记录看起来就是多条互不相关的记录。
- 实盘绑定只有 `live_sessions.backtest_record_id` 一个字段，是**单组合**语义；没有 `pairing_plan_id` / `backtest_run_group_id`。
- 「拼盘」不是组合页的新对象；组合页的主从设置与拼盘无关，保持原样。

### 12.2 操作流程

入口固定为：**回测管理 → 「+ 新建拼盘」**。向导共 7 步，每步都可取消；所有「下一步」都只在当前步校验通过后可用。

| 步骤 | 输入 | 产出 | 失败分支 | 用户可见提示 |
|---|---|---|---|---|
| 1 挑主 | 范围（L2 同组合 / L3 跨组合）、主出资方 | `main_ref` + 只读资格快照 | 无合格对象 → 空状态；资格不过 → 禁止下一步 | 「主出资方必须先有一份完成的回测；参数改过要重跑」 |
| 2 挑搭配 | 1 个（默认）或 2–3 个（E 阶段）对象 | `member_refs` 草稿 | 超上限 → 排队/拒绝/手动；资格不过 → 勾选框禁用；与现有成员预检失败 → 不能加入 | 候选列表**只显示资格与静态属性，不显示全期收益排名**；现金出口显示通道/期限/回流日 |
| 3 资格校验 | 草稿成员 | 每个成员的资格快照（E1–E12 或 C1–C8） | `STALE` / 未冻结 / 回测未完成 → 阻断 | 逐条通过/失败，可点击跳到回测记录或出口验证记录；失败不可「忽略」 |
| 4 搭配评估 | 共同 OOS 窗口、阈值版本 | `capital_pairing_evals`：H1–H8、八组特征、GO/WATCH/NO_GO | NO_GO → 不能进入回测；可换成员重评 | 必须展示特征值、阈值、样本量、IS/OOS 分栏与理由；不允许只给一个总分 |
| 5 联合回测 | 区间、分红、执行/容量版本、资金池版本、基线开关 | L2：一条 `backtest_records`；L3：一个 `backtest_run_groups` + N 条成员记录 + 聚合曲线 | 数据不足 → 不落记录；运行失败 → 失败状态；取消 → `canceled`；超过 3 个 → 不允许 | 进度、预计耗时、基线清单；「结果只是证据，不是上线许可」 |
| 6 生成拼盘 | 名称、生效期、额度/借期/召回、池范围、归属策略、现金出口参数 | `capital_pairing_plans`（APPROVED）+ `pairing_version` + 证据引用 | 证据缺失/过期/哈希漂移/NO_GO → 阻断 | 「拼盘是配置对象，不是新的结果表」；展示证据链接与冻结时间 |
| 7 实盘绑定 | 会话、真实资金、拼盘 | `live_sessions.pairing_plan_id` + `backtest_run_group_id` + 继承快照 | 未 APPROVED、成员与会话组合不一致、资金不足、阶段 < F → 拒绝/禁用 | F 阶段只影子不执行；G 才生效；显示继承矩阵与不可复现因素 |

关键规则：

- **顺序不可颠倒**：先选人，再评估，再回测。候选列表不得提前展示全期业绩排名，否则就是「先知道谁表现好再决定借给谁」。
- **评估与回测分离**：评估回答「值不值得搭」，回测回答「搭了以后资金池怎么走」；评估 NO_GO 时不允许用「回测收益高」强行覆盖。
- **联合回测必须建模资金池**：阶段 B/E 要把 LoanLot、额度、召回、门控释放接进回测。当前 `run_multi` 各组合现金独立、不跨组合划转（代码内联注释为准；顶部 docstring 与 `MultiBacktestRequest` 的「共享可用额」描述已过期），所以**现有 run-multi 只能当「独立资金 + 容量共享」基线，不能当 0019 资金池证据**。
- **基线同批生成**：各自单独跑、静态等额、静态比例、动态池；参数哈希与区间一致的旧记录可以复用，否则重跑，并记录复用关系。
- **现金出口不参与收益相关性/同票重叠**：它没有信号，评估展示的是收益率、期限、限额、回流确定性，见 §13。

取消/回退/重来：

| 时点 | 操作 | 已产生的数据 | 重新开始 |
|---|---|---|---|
| 第 1–4 步 | 关闭向导 | 默认不落库；用户主动「保存草稿」才落 `DRAFT` | 重新打开，草稿可继续 |
| 评估完成、未回测 | 改成员 | 原评估置 `STALE`，旧 eval 保留为历史 | 必须重评，不能沿用旧结论 |
| 回测运行中 | 取消 | 运行组/成员记录置 `canceled`；拼盘回到 `EVALUATED` | 取消的证据不可复用，必须重跑 |
| 回测完成、未批准 | 重跑 | 新记录/新运行组；旧证据标 `superseded` 但保留 | 生成新版本，不覆盖旧结果 |
| 已批准、未绑定 | 归档 | 方案 `ARCHIVED`；证据保留 | 改成员必须新建版本（`pairing_version + 1`） |
| 已绑定实盘 | 解绑 | 停会话或下次启动生效；方案 `RETIRED` | 新版本重新走 1–7 步，禁止原地改成员 |
| 删除 | 仅未绑定方案可删 | 软删方案；回测记录不删 | 证据可追溯 |

### 12.3 拼盘在数据上是什么

**结论：`拼盘 = 一条多组合回测记录` 这个说法不成立（至少不完整）。**

- **L2（同一组合内多策略）**：可以成立。证据就是该组合的一条普通 `backtest_records`；前提是阶段 B 已把借贷建模进单组合回测，并在快照里写入 `loan_model_version`。
- **L3（跨组合）**：不成立。一次联合回测落库是 **1 个 `backtest_run_groups` + N 条 `backtest_records` + `aggregate_json`**；没有任何一条 `backtest_records` 能同时表达 N 个组合的归属、成员明细和聚合曲线。
- **拼盘本身**是配置对象，不是结果：`capital_pairing_plans`（头）+ `capital_pairings`（边）+ `capital_pairing_evals`（评估与冻结指标）+ 证据引用。用户看到的「拼盘结果」= 方案摘要 + 证据（L2 记录 / L3 运行组及成员）。

数据关系：

| 实体 | 现状 | 在拼盘中的角色 | 处理 |
|---|---|---|---|
| `backtest_records` | 每组合一条，已有详情/对比/评估 | L2 证据；L3 成员记录 | 复用，不改结果口径 |
| `backtest_run_groups` | 已有头 + `aggregate_json`，前端无入口 | L3 证据容器 | 增列 `pairing_plan_id`（可空）；补前端入口与分组展示 |
| `backtest_evaluations` | 按记录冻结指标 | 成员指标来源 | 复用；不回写、不重算 |
| `capital_pairing_plans` | 新增 | 拼盘头：成员、角色、额度/借期、状态、版本、证据引用 | 新表 |
| `capital_pairings` | 新增（§5.1） | 拼盘边：出借方→借款方 | 新表 |
| `capital_pairing_evals` | 新增 | 搭配评估、基线对比、GO/WATCH/NO_GO | 新表 |
| `live_sessions` | 只有 `backtest_record_id` | 绑定拼盘 | 增列 `pairing_plan_id`、`backtest_run_group_id`；与 `backtest_record_id` 二选一，后两者成对出现 |

为什么不能只用现有记录：

1. L3 的成员是 N 个组合，单条记录只能挂一个 `portfolio_strategy_id`。
2. `backtest_records` 没有生命周期、版本、资格快照、绑定状态；把这些塞进记录会污染回测语义。
3. 拼盘要能「批准/影子/生效/暂停/退役」，这些状态不属于一次回测。
4. 实盘要绑定的是「整套搭配」，不是某一条成员记录；绑错一条会静默丢失其他成员。

为什么不再建一张「拼盘结果表」：

1. 会复制收益/回撤/Sharpe，出现两套口径，日后必然漂移。
2. 现有详情、对比、分析页都按记录组织；复制一份等于重做一套钻取。
3. 正确做法是：成员指标引用 `backtest_evaluations`，聚合指标由 `aggregate_json` + 成员快照一次性计算后冻结在 `capital_pairing_evals`，展示层只读冻结值。

当前缺口（必须在 E 阶段补齐）：

| 缺口 | 现状 | 影响 |
|---|---|---|
| 多组合回测前端入口 | 只有后端 `/run-multi` 与运行组接口，web 无 API 客户端 | 用户无法发起 L3 |
| 记录未暴露运行组 | `_serialize_record` 不返回 `run_group_id` | 成员记录在列表里不可分组、无法折叠 |
| 聚合指标不全 | `aggregate_json` 只有权益/回撤/成员/初始资金 | 组合级 Sharpe/Calmar/换手需在评估表冻结 |
| 实盘绑定单记录 | `live_sessions.backtest_record_id` | 拼盘会被错误地绑成某一个成员 |
| 回测无跨组合借贷 | `run_multi` 各组合现金独立 | 不能直接作为资金池证据 |
| 运行组取消语义不清 | 只有单条记录取消接口；取消任一子记录会中止整批，但没有独立的组级接口、权限和提示 | 用户无法明确「整组取消」，容易误以为只停一条 |

### 12.4 与现有页面的冲突与复用

## 13. 借款方分类与现金管理定位

### 13.1 两类借款方，不能共用一套判据

| `borrower_type` | 它是什么 | 证据 | 判据 | 为什么 |
|---|---|---|---|---|
| `strategy` / `portfolio` | 产生 alpha 的策略或组合 | 已完成回测 + 冻结指标 | E1–E12 + H1–H8 | 未来收益不确定，只能用历史与样本外推断 |
| `cash_outlet` | 把闲置资金放出去的通道/产品（逆回购、货基 ETF、券商现金理财） | 通道验证 + 收益率曲线 + 结算规则 | C1–C8（§13.2） | 它没有信号、没有 alpha；收益是约定/市场利率，不是策略能力。要求它「先回测」是范畴错误 |

为什么现金出口**不需要、也不可能**有策略回测资格：

- 没有可复现的下单决策：出口的「买卖」是资金调度，不是信号；同样的输入只会得到「放/不放」和期限选择，不存在策略胜率。
- 收益不是 alpha：逆回购锁定利率、货基给万份收益，都是市场/合约结果；把它塞进策略回测，只会把利率曲线伪装成策略曲线。
- 回测证明不了执行：能不能下单、何时到账、限额多少，只有通道验证和对账能回答；回测再漂亮也不能替代 C1/C8。
- 正确的证据链是：通道验证 → 小额实盘 → 回流时点对账 → 收益率曲线用于估算，而不是「先跑十年回测」。

判断口径：

- 策略类问：「它过去做得怎么样、参数变没变、未来还能不能做？」
- 现金出口问：「这笔钱放进去，能不能在约定时点、按可验证收益率、按可接受风险回来？」
- **定位**：现金管理是资金池的一个现金出口（`borrower_type=cash_outlet`），不是固收策略，也不是独立账户；它不参与策略排名、不参与收益相关性/同票/门控特征，只参与「空闲额度能放多久、何时必须回来」。

### 13.2 现金出口判据 C1–C8

| 编号 | 判据 | 要回答的问题 | 通过标准（建议） |
|---|---|---|---|
| C1 | 通道可下单 | 现有通道（通达信 TQ / QMT / 掘金桥）能否下单、撤单、查成交？是否需要额外权限？ | 至少一条可编程通道完成只读+下单验证；否则只能人工 |
| C2 | 收益率数据 | 收益率/万份收益从哪里来、频率、历史长度、能否回溯？ | 有可追溯的日频序列 ≥ 60 日；否则只用当前报价并标注「不可回测」 |
| C3 | 流动性 | T+0 / T+1 / 到期日？遇节假日如何顺延？到账时点？ | 明确最晚可用日；首期只接受 T+0 或 ≤ 7 天到期 |
| C4 | 限额 | 单笔最小/最大、单日总额、单账户上限、最小递增单位？ | 可配置且能事前校验；最小单位不得导致碎片化 |
| C5 | 赎回/提前支取 | 能否提前赎回？罚息？快速赎回额度？ | 首期只接受可确定退出或到期自动回款的品种 |
| C6 | 风险等级 | 产品风险等级、信用/交易对手/流动性风险？是否保本？ | 只接受 R1/R2；不得假设保本 |
| C7 | 资金回流确定性 | 最晚可用日、可用 vs 可取、失败兜底？ | 到期日 + 缓冲 ≤ 借款方下次用钱日；否则拒绝 |
| C8 | 通道验证 | 是否完成小额实盘验证（申购/赎回/到期/对账）？ | 有验证记录、金额、时间、结果；有效期默认 1 年 |

拒绝码：`CHANNEL_UNSUPPORTED`、`YIELD_DATA_MISSING`、`LIQUIDITY_MISMATCH`、`LIMIT_TOO_SMALL`、`REDEMPTION_RESTRICTED`、`RISK_LEVEL_HIGH`、`SETTLEMENT_UNCERTAIN`、`OUTLET_NOT_VERIFIED`。

注意：C1/C8 是运行验证，不是回测；一个产品没有策略回测，仍可能通过 C1–C8 成为合格出口。反过来，历史收益再高，只要通道下不了单或回流不确定，也不能借。

### 13.3 可选标的与通道现实

| 类别 | 例子 | 现有通道可能性 | 限制/权限 | 首期建议 |
|---|---|---|---|---|
| 交易所逆回购 | GC001/GC007（沪 204001/204007）、深 131810/131811 | 取决于券商是否开放回购权限与 API；需实测 | 最小参与金额与递增单位以交易所/券商为准；到期自动回款；不能提前赎回 | **首选**：1 天期先跑通，7 天期加缓冲 |
| 货基 ETF | 511990、511880、511660 等 | 场内买卖，取决于券商与桥的 ETF 支持 | 100 份起；T+0 交易以券商规则为准；有折溢价 | 次选：先验证卖出后资金可用时点 |
| 券商现金理财 | 券商保证金理财/现金管理产品 | 通常需单独签约，**多数无交易所 API** | 快速赎回有额度；可能 T+1 | 首期排除，除非通道确认 |
| 银行存款/通知存款 | 对公/个人存款 | 无交易 API | 无法自动执行 | 排除 |
| 国债逆回购跨市场 | 跨市场品种 | 需额外权限 | 规则差异大 | 暂不做 |

**不要在文档或界面里假设「现在就能下单」**：每个品种必须在 `cash_outlets` 注册表里记录通道、权限、验证状态；未验证的一律 `OUTLET_NOT_VERIFIED`。

入口规划（避免和现有「现金管理增强（预留）」混淆）：

- **配置与验证**：实盘交易 → 会话详情 →「现金出口」卡片（新增，F 阶段）：白名单、通道、期限上限、单笔/单日限额、验证状态、最近一次对账。
- **评估与建议**：回测管理 → 新建拼盘 → 搭配对象选「现金出口」（C 阶段，只读计划建议，不触达实盘）。
- **执行**：G 前段在「现金出口」卡片内人工确认；G 后段才允许自动。F 阶段只做通道小额验证（C8）与只读影子，不执行生产金额。组合页现有的「现金管理增强（预留）」开关保留为**阈值来源**，不再承担执行动作。

### 13.4 资金口径与对账

四个量必须分开，不能用一个 `cash` 混着算：

```text
available_cash      可买股票的现金（下单校验用）
withdrawable_cash   可取现金（T+1 等柜台规则）
outlet_principal    已放进出口的本金
outlet_pending      已报单未确认/在途的出口金额
accrued_interest    已计提未到账收益
```

规则：

- 申购/买入出口：`available_cash -= 金额 + 费用`，`outlet_principal += 本金`；未成交放 `outlet_pending`，不计息、不可再借。
- 到期/赎回：按**实际可用时点**回补 `available_cash`；T+1 品种当日只记 `outlet_pending` 回流，不当作可买。
- 总资产口径：`cash_account + outlet_principal + accrued_interest + 股票市值`；策略归因只看法币股票部分，出口收益单列。
- 对账恒等式：`券商现金 + 出口本金 + 出口应计 + 股票市值 = 总资产`；每日与柜台对账，差异超阈值冻结出口。
- 防负现金：出口申购只能从 0019 的 `Lendable` 出，不得占用 `PENDING_RELEASE`、在途买入预留、`min_cash_reserve`。

### 13.5 与资金池的接口

- 出口是借款方：`borrower_type=cash_outlet`、`max_share`、`loan_term_days`、`due_at`。可借额沿用 0019 §3 的 `Lendable` 公式，出口不得突破 `cash_outlet_max_share`。
- 硬条件：`due_at + cash_outlet_min_buffer_days ≤ 出借方下次用钱日`；不满足就缩短期限或拒绝。
- 召回：门控恢复/出借方有信号 → `PENDING_RECALL`；T+0 品种当日召回，T+1/到期品种只能停止新增并等待，不得假装能立刻拿回。
- `PENDING_RELEASE` / `PENDING_RECALL` 不计入可借；出口在途也不计入。
- 回流失败 → `outlet_shortfall` 事件，出借方次日优先补足；同一个月两次 shortfall → 出口 `SUSPENDED`。
- 现金收益记 `cash_yield_contribution`，不进入策略 Sharpe/胜率/超额；组合总收益可以单列一行。

### 13.6 回测侧怎么建模

- **用收益率曲线，不用价格序列**：`interest_t = principal × rate_t / 365 × days`；逆回购用买入时锁定利率，货基用万份收益/7 日年化（保守取近 N 日下四分位），现金理财用公布利率并标注「不保证」。
- **可用性建模**：申购日 T 收盘扣 `available`，T+1（或 T+0）才回补；这段时间不能买股票。到期遇节假日按规则顺延。
- **费用与限额**：手续费、最低起点、整数倍、单日上限都要进模型；否则回测会高估可投金额。
- **无前视**：只用决策时点已知的利率/净值；不得用当日收盘后才公布的收益。
- **归因分离**：出口收益单独一行；策略指标（收益、回撤、Sharpe）不包含它；组合总收益包含，但必须能拆出 `cash_yield_contribution`。
- **版本**：快照写 `cash_outlet_model_version`；模型变化后旧结果标「不可比」。
- **边界**：回测只能估收益与资金占用，不能证明通道能下单；执行可行性靠 C1/C8 的实盘验证。

### 13.7 风险与缓解

| 风险 | 场景 | 缓解 |
|---|---|---|
| 次日买入可用不足 | 钱在出口未回，策略次日开盘要买 | 到期日+缓冲校验；保留 `min_cash_reserve`；首期只做 T+0/1 天 |
| 赎回受限 | 快速赎回额度用完、产品暂停赎回 | 白名单；期限上限；受限品种不做自动 |
| 账实不符 | 柜台已回款、虚拟账本未记 | 每日对账；差异即冻结出口并告警 |
| 自动执行误操作 | 金额算错、标的下错、重复下单 | 默认建议单+人工确认；单笔/单日上限；kill switch |
| 收益不达预期 | 用最高宣传收益 | 用保守利率；展示「最低/中位/最高」三档，不承诺 |
| 通道/产品变更 | 券商关闭权限、产品清盘 | C1/C8 定期复验；变更即 `STALE` |

### 13.8 落地路径：半自动是否合理

用户提出的「先半自动（建议单 + 人工确认）→ 验证资金口径与回流 → 再全自动」方向是对的，但建议再往前加一个**只读影子**阶段，并把首期品种限制得更窄：

| 阶段 | 做什么 | 执行 | 时长/门槛 | 目的 |
|---|---|---|---|---|
| P0 只读影子 | 每日生成建议（金额、标的、期限、预计回流），不下单 | 无 | 10 个交易日 | 验证建议金额与真实可用资金、次日买入需求是否冲突 |
| P1 人工确认执行 | 建议单 + 人工确认后执行，限 T+0/1 天品种、单笔上限 | 人工 | 20 个交易日 | 验证下单、撤单、到期回款、对账 |
| P2 半自动 | 系统生成 + 一键确认；仍限白名单与期限 | 一键 | 20 个交易日 | 验证稳定性与异常处理 |
| P3 全自动 | 仅对已验证的 T+0/≤7 天品种，额度上限内自动；自动召回 | 自动 | 连续 2 个月无 shortfall、对账全绿 | 放开 |

阶段归属：P0 属 **F**（只读影子）；P1–P2 属 **G 前段**；P3 属 **G 后段**。F 阶段允许的实盘动作只有 C8 的通道小额验证（单独审批、单笔上限、可随时停止），不得执行生产金额。

为什么更稳：

1. 主要风险不是收益，而是**回流时点与可用资金**；只读影子能先暴露「建议金额过大、次日要买」的冲突。
2. 先做 1 天期逆回购/T+0 ETF，能把「到期/卖出→可用」的规则跑清楚；长期限逆回购一旦锁住，召回模型再完美也拿不回来。
3. 券商现金理财多数没有 API，不应作为首期自动化的目标；等通道确认后再评估。
4. 不建议「先全自动再补对账」：现金出口的错误会直接造成次日买不进或账实不符，修复成本高于收益。

**界面：**

- 用户打开后，只会在决策事件/工作台的事件流里看到 `gate=cash_enhance_trigger`（中文标签「现金增强触发」），**不会看到任何委托、成交、资金变化**。
- 0019 规划的 `cash_management` 归属选项尚未落地；现有实盘会话的 `capital_pool_mode` 只有 `off / equal / risk_budget / priority`，没有现金出口选项，也不能把闲置资金自动转成逆回购或货基。

**结论：当前是「纯占位 / 只记录事件」，不是可用功能。** 本文 §13.2–§13.8 是升级方案，不代表已实现；在 G 验收通过前，界面必须继续标「预留」，文档、演示、汇报都不能说成「已经能自动理财」。

### 13.10 现金出口的验收

- C1–C8 每一条都有可查记录；未验证品种 0 个进入可借清单。
- 只读影子 10 日：建议金额与次日买入需求冲突 0 次；预计回流日与实际回流日偏差 ≤ 1 个交易日。
- 人工执行 20 日：对账全绿、负现金 0、shortfall 0。
- 收益归因：`cash_yield_contribution` 与策略收益完全分开，策略指标不受影响。
- 召回演练：门控恢复时，T+0 品种当日回到可用；T+1/到期品种在预计日回到可用，shortfall 记录可解释。
- 任意一次账实不符 → 自动暂停出口，人工复核后才恢复。
