## 0. 执行规约（全程适用）

1. **串行单负责人**：一个批次一个 commit，先实现 → 聚焦 pytest / 必要 vitest → 提交 → 推送 → 汇报。不开并行分支。
2. **默认关闭**：所有新增能力默认关闭；关闭时插入点第一行即返回，`params_snapshot` 显式写否定值（区分"功能关闭"与"旧记录缺键"）。
3. **同源判定**：判定内核只有一份（`core/engine/`），回测/实盘各自只负责"取事件"与"落账"，不允许只写一侧。
4. **口径可冻结**：会改变历史结果的开关进 `params_snapshot` + 增量 `schema_fingerprint`；开关或内核版本一变 → 旧接缝判废、新旧记录不混比。
5. **迁移单头**：每批实施前 `alembic heads` + 目录扫描确认 revision 未占用，逐条串行接在上一批之后，`upgrade`/`downgrade` 双向可用；SQLite 加列统一 `op.batch_alter_table`。
6. **测试边界**：全程只跑聚焦测试（会冻结通达信客户端）；不跑全量、不重启后端、不启停实盘会话、不改库内业务数据、不碰真实 webhook/secret。
7. **文档同轮收口**：每批同步 `docs/用户使用说明.md`「九、系统配置」与 `AGENTS.md` 对应业务规则段。

**批次 2 决策（方案未覆盖处，按「默认关闭 + 最小侵入 + 可回退」拍定）**
1. **多组合的资金口径 = 各组合虚拟现金独立、互不划转**（0010 §5.1 原话「不做组合间调仓/资金划转」）。审批内核按「组合在用户给定顺序中的先后」串行调用，每笔的可用额 = 本组合 `cash − 本组合在途 BUY 金额`；「同一时刻可用现金池」以不变量「Σ 通过金额 ≤ Σ 可用现金」保证（各组合都不超自身可用 ⇒ 恒成立）。**不实现跨组合转账**：转账会让出资组合的虚拟净值凭空下跌（假回撤，可能误触 max_drawdown 熔断），且与「各组合独立记账」的既有语义冲突。
2. `partial_fill` 只作用于 **BUY**：卖出残量继续按既有「下一个 bar 重试/超时撤单」处理，避免新增卖出侧状态机。
3. `realistic` 只展开既有四个开关（涨跌停/成交量/自适应滑点/日终抬峰），不新增成交价模型，保证与既有 `run` 单组合路径可交叉验证。
4. `run_multi` 的基准序列取**第一个组合**的 `benchmark_index`（一条曲线无法同时对齐多个基准），聚合曲线只做展示/对照，不写 `backtest_daily_snapshots`。
5. 时点成分的「同步」按**用户操作当日**写区间（新增开区间、消失关区间含当日）：不回溯改历史区间，避免每次同步把历史成分覆盖成"当前池"（这正是 J7 要解决的问题）。
6. `run_multi` 的 `insufficient_cash` 事件参数名用 `available_cash`（而非实盘的 `shared_cash`），如实反映「本组合可用额」口径；文案仍与实盘同构。


### 批次 3（M1、I1）

**M1 半自动审批队列**
- 表：`live_approval_queue`（迁移 `f3a4b5c6d7e8`）：`live_session_id`（FK CASCADE）/`portfolio_strategy_id`（FK RESTRICT）/`strategy_id`/`stock_code`/`trade_type`/`price`/`quantity`/`signal_type`/`signal_name`/`period`/`bar_time`/`signal_bar_date`/`status`（pending/approved/rejected/expired/dropped）/`reason`/`decided_at`/`expires_at`/`created_at`，索引 `(session_id, status)` 与 `expires_at`。
- 开关：既有的 `live_sessions.execution_mode="manual"`（此前白名单只有 alert/auto，本次加入 manual）。**默认不开**：新建会话默认 alert，历史会话值不变 → 与改动前逐字一致。
- 插入点：`LiveEngine._submit_one_order` 的「① 审批 + 拆单 + submitted 落库注册」**之前**入队并返回；`_manual_order`/`_approval_passed`/`_split_child`/`_requote` 四类订单不重复入队。

**I1 人工补单 / 平仓 / 改账**
- 表：`live_manual_actions`（同一条迁移）：`action_type` ∈ manual_order/force_close/cash_adjust/position_adjust、`result` ∈ accepted/blocked/rejected/applied、`stock_code`/`trade_type`/`quantity`/`price`/`live_order_id`/`cash_delta`/`reason`/`created_at`，索引 `(session_id, created_at)`。
- 人工补单（`LiveEngine.submit_manual_order`）：仅 `execution_mode=manual` 开放；`_manual_order=True` → 不入审批队列、不参与 `bought_today` 信号级排重、不参与让价（`_manual_price_bias` 直接返回）；仍走 `_submit_one_order` 的**全部**闸门与拆单/落库路径。单笔金额上限 `tq_trade.manual_order_max_amount`（默认 0 = 不限），同名操作最小间隔 `tq_trade.manual_action_min_interval_ms`（默认 1000 ms，防误触连点）。
- 人工平仓（`force_close_position`）：按虚拟持仓全额生成 SELL CLOSE；`live_sell_scope=platform_only` 下纯外部仓（`platform_quantity<=0`）拒绝（409 + `result=blocked` 审计），与策略卖单同一口径。
- 现金改账：复用 `live_service.record_cash_flow`（运行中 `apply_cash_flow` 立即生效，停止时下次启动重放），另落一条 `cash_adjust` 审计（`cash_delta` = 有符号实际入账额）。
- 持仓改账（`adjust_position_virtual`，**仅停止的会话**）：写一笔合成 `live_trades`（`live_order_id=NULL`、佣金/印花税 0），重启 `recover` 重放即生效——虚拟持仓/虚拟现金的唯一权威来源就是 `live_trades` 重放，不再新增读取路径。运行中会话拒绝（409）：内存态正被引擎使用，直接改库会造成「本次运行与重启后不一致」。
- API：`POST /api/live/sessions/{id}/manual/orders|close|cash-adjust|position-adjust`、`GET .../manual/actions`（审计倒序）。
- 回退：`execution_mode != manual` 时入队分支第一行即返回；人工端点要么 409（非 manual / 未运行），要么写 `live_manual_actions` 一行审计后调用既有路径；`manual_order_max_amount=0`、`manual_action_min_interval_ms=0` 等价不限制。

**批次 3 决策（方案未覆盖处，按「默认关闭 + 最小侵入 + 可回退」拍定）**
1. **manual 会话不走盘前集合竞价**：`_maybe_pre_open_auction` 既有条件 `execution_mode != "auto" → return`，manual 自然被排除；待批单在 09:31 首根 1m bar 释放时入队（与定时段的排队语义一致），避免「09:15 入队、09:20 批准、按信号价追价」的双口径。
2. **入队判断在 `bought_today` / 槽位 / 在途判重之后**（而不是之前）：队列里不出现「今天已买过/已满仓」的必死单；批准时这些闸门再跑一次（双保险，代价是同一批信号可能被拒两次，事件各留一条，可接受）。
3. **`signal_bar_date` 随行落库**（而非批准时按 `bar_time.date()` 重建）：日线信号在 15:05 收盘轮次产生时 `signal_bar_date=NULL`，若按 `bar_time.date()` 重建会被误顺延次日；分钟信号则相反。原值还原是唯一不改变 B-1 语义的做法。
4. **人工平仓不绕过 `live_sell_scope`**：该配置是账户级口径（卖整仓 vs 只卖平台自建），人工操作若绕过会让「同一配置两种行为」；要卖纯外部仓请改配置或柜台操作。
5. **持仓改账用合成成交而非新增虚拟账本**：`recover` 的唯一输入是 `live_trades`，合成行 = 与真实成交同一口径，回测/实盘对账、净值曲线、熔断基准全部自动一致，零新增读取路径。
6. **人工单归因策略**：请求可带 `strategy_id`，缺省取组合内第一个策略（`_manual_ctx`）。原因：`live_trades.strategy_id`、槽位计数、`bought_today` 都以策略为键，必须有一个归属；前端按组合操作时不必知道策略 id。


### 批次 4（C1、C2、C3、I2）

**C1 对账差异台账（默认关闭）**
- 表：`live_reconciliation_diffs`（迁移 `f4b5c6d7e8f9`）：`live_session_id`（FK CASCADE）/`portfolio_strategy_id`/`diff_type` ∈ position/cash/equity/`stock_code`/`expected`/`actual`/`delta`（Numeric(18,4)）/`status` ∈ pending/accepted/resolved/ignored/`resolution`/`detail`/`created_at`/`updated_at`，索引 `(session_id, status)` 与 `(session_id, diff_type, stock_code)`。
- 开关：`tq_trade.reconciliation_ledger_enabled`（默认 **false**）。关闭时 `_note_reconciliation_diff` 第一行返回，既有告警/决策事件/记账全部逐字不变。
- 插入点（全部在既有告警发射**之后**，旁路）：`_note_cash_diff`（cash）、`_note_equity_deviation`（equity）、`_note_manual_intervention`（position，`detail` 带 `price=` 提示供改账取价）。
- 去重：同一 `(session, diff_type, stock_code)` 的 pending 行复用更新（差异未处理期间数值来回变，逐次追加会把台账刷成噪声）。
- 状态机：`pending → accepted | resolved | ignored`；已处理行不能再次处理（400）。

**C2 现金流红冲（禁止物理删除）**
- 表：`live_cash_flows` 同迁移加 `reversal_of_id` / `reversed_by_id`（自引用 FK `ON DELETE SET NULL`）/ `voided`（Boolean，默认 0）。
- 语义：红冲 = 反向补一笔（同 `flow_type`、`amount` 取反、`reversal_of_id=原行`），原行 `reversed_by_id`+`voided=1`；Σamount 口径自动归零，净值（总市值 − 累计净流入）无需额外处理。同一笔只能冲一次，红冲行不能再被红冲。
- 运行中会话即时 `engine.apply_cash_flow(反向额)`；停止时下次 `recover` 重放。

**C3 现金流日期边界**
- `record_cash_flow`：`flow_date` 晚于今天 → 拒绝（未来入金会把净流入提前计进今天的净值口径）；早于 `live_sessions.created_at.date()`（会话起账日）→ 拒绝，除非显式 `allow_backfill=true`（会改写历史净值口径，必须显式确认）。
- API `POST /cash-flows` 透传 `allow_backfill`（缺省 false）。

**I2 接受柜台口径（差异闭环的改账动作）**
- `resolve_reconciliation_diff(action="accept")`：`position` 差 → `delta = actual − expected`，价格优先请求 `price`、其次 `detail` 的 `price=` 提示；运行中调 `engine.accept_counter_truth(...)` 同步内存 + 落合成 `live_trades`（与 I1 持仓改账同一口径），停止时直接 `adjust_position_virtual`（重启重放生效）。
- `cash`/`equity` 的 accept **只确认口径不改账**（既有规则明确「现金差只告警不改账」，不能借差异闭环偷偷改虚拟现金）。
- API：`GET /api/live/sessions/{id}/diffs?status=`、`POST .../diffs/{did}/resolve`（body `action`/`resolution`/`price`）、`POST .../cash-flows/{fid}/reverse`。

**批次 4 决策（方案未覆盖处，按「默认关闭 + 最小侵入 + 可回退」拍定）**
1. **差异台账默认关闭**：既有 `cash_diff` / `equity_deviation` / `manual_intervention` 已经是成熟告警链，台账是「可闭环」增强；默认开启会让每次账户刷新多一次写库（SQLite 单写者），不符合最小侵入。
2. **台账不做自动处置**：pending 行不会自动改账、不会自动消失；accept 必须人工显式触发，且改账走既有合成成交路径（唯一权威来源仍是 `live_trades` 重放）。
3. **红冲不改原行金额/类型**：只加 `voided` 标记与反向行，保证「历史流水一个字都不改」，审计可逐笔展开。
4. **`allow_backfill` 是显式布尔而非日期判断**：会话起账日只是启发式（历史会话 `created_at` 可能早于首笔真实入账），是否允许改写历史必须由操作者确认。
5. **`_note_manual_intervention` 增加可选 `portfolio_id`**：持仓差必须知道归属组合才能改账；四个调用点都在循环内有 `port`，直接传入，不改变既有行为（缺省 None 时只登记不归属）。


### 批次 5（C4 对账日报 / I4 手工成交 / I3 池外仓处置 / C5 公司行为台账）

**C4 每日对账日报（默认开启，只读聚合）**
- 表：`live_reconciliation_reports`（迁移 `f5c6d7e8f9a0`），唯一键 `(live_session_id, report_date)`，重复生成只覆盖不追加。

- 数据源：柜台侧取最新 `live_account_snapshots`；虚拟侧取运行中引擎内存（`account.cash` + `virtual_equity()` + 各策略持仓）。**只在运行中生成**：停止的会话没有可信的柜台同刻快照，宁缺毋滥。

**I4 手工成交录入**
- 场景：电话委托/其他终端已成交，平台没看见回报；把既成事实补进虚拟账本，避免现金/持仓长期漂移。
- 实现：`LiveEngine.submit_manual_trade(...)` 直接落 `live_orders(order_type="manual", status="filled", signal_name="手工成交录入…")` + `live_trades`，再调与真实成交回报**完全相同**的 `_apply_filled_trade`（持仓/现金/成本/风控冷静期/策略归因一次到位）。**不经过桥、不占审批、不做买入闸门**——成交已发生，闸门在这里只会有害。
- 归因：`strategy_id` 缺省取组合内第一个策略（同 I1）；`signal_type` 按持仓自动判：BUY 无仓=OPEN/有仓=ADD；SELL 清仓=CLOSE/减仓=REDUCE。
- 校验：仅 `execution_mode=manual` 会话开放；卖出必须有虚拟持仓且数量 ≤ 持仓（超卖直接拒绝，不做静默缩量）；买入不检查虚拟现金（允许负现金，差异由对账暴露）。
- 费用：`commission` 缺省 0，应按柜台实际填写；`stamp_duty` 记 0。费用录错会以 `cash_diff` 形式进入对账，不影响持仓。
- API：`POST /api/live/sessions/{id}/manual/trades`（body：`portfolio_strategy_id`/`stock_code`/`trade_type`/`quantity`/`price`/`strategy_id`/`commission`/`note`）。
- 决策：不做「撤销手工成交」——错误录入用反向手工成交（或停止后用 `adjust_position_virtual` / 现金流红冲）修正，保持「历史只追加」。

**I3 池外外部仓处置**
- 表：`live_out_of_pool_decisions`（迁移 `f6d7e8f9a0b1`），唯一键 `(session, stock_code)`，`action` ∈ include/ignore，`portfolio_strategy_id`/`note` 留痕。
- 语义：池外仓默认仍是「不归属、不参与风控、平台不代卖、只在展示层可见」（**默认语义不变**）。本条目只提供人工显式处置入口。
- include（一键纳入）：把代码写入该组合当前股票池 `stock_pool_stocks`；组合开启 PIT 时同步补一条 `effective_from=今天、effective_to=NULL、source=manual` 的成员区间。下一轮持仓采集（60s）自动按池内继承仓导入虚拟账本并扣减该组合配置资金。
- ignore（永久忽略）：只抑制 `out_of_pool_position` 告警（SSE risk + 每日汇总决策事件）；仓位仍在展示层可见、仍不参与风控/不代卖。
- 引擎：`_report_out_of_pool` 首次调用时懒加载 ignore 集合（未迁移表时静默为空集）；处置后 API 直接刷新运行中引擎内存（`reload_out_of_pool_decisions` / `include_pool_code`），include 立即加入内存池代码，无需重启。

- 决策：include 不自动触发一次立即采集——归属/现金扣减仍走既有 `_import_external_positions` 的幂等路径，避免在 API 请求线程里制造第二个记账入口。

**C5 实盘公司行为显式台账（启发式送转）**
- 现状：手工 `corporate_actions` 事件应用后已写 `live_corporate_actions`；但柜台镜面**启发式识别**到的送转/拆股只打日志，重启后无法追溯「某天股数为什么变了」。

- 幂等：复用表唯一键 `(session, 组合, code, event_type, ex_date)`，`on_conflict_do_nothing`；同一天重复镜面不追加。
- 事务：用 `begin_nested()` 保存点隔离，台账写失败只告警，不提前 commit、不回滚整轮镜面（真正提交仍在 `_apply_bridge_account_snapshot` 末尾）。
- API：`GET /api/live/sessions/{id}/corporate-actions?limit=200`（按生效日倒序），手工事件与启发式事件同表可对照。


### 批次 6（D1、D2、D3、M2、A3）

**D1 账户级聚合熔断（默认关闭）**
- 表/列：迁移 `b8c9d0e1f2a3` 给 `live_sessions` 加 `account_risk_enabled`(默认 0)/`account_max_drawdown`(可空)/`account_daily_loss_limit`(可空)/`account_risk_state`(JSON 文本)；账户聚合口径 = Σ 各组合 `risk_equity()`（现金 + 持仓市值 − 累计外部净流入），与组合级同源。
- 开关/默认值：`account_risk_enabled=0` 时 `AccountRiskService` 首行返回，不读表不写状态；阈值缺省取 `tq_trade.account_max_drawdown`/`account_daily_loss_limit`（缺键 0.15/0.05），会话列显式填值覆盖。

**D2 60/80/100% 分级预警**

**批次 6 决策（方案未覆盖处，按「默认关闭 + 最小侵入 + 可回退」拍定）**
1. **账户级阈值默认不继承组合阈值**：多组合阈值可能各不相同，取加权平均会产生「谁都说不清」的线；缺省用固定 15%/5%（config 可改），会话列可显式覆盖。组合级熔断保持原样，两层独立生效（任一触发都停开仓）。
2. **账户熔断只剥 BUY、不减仓**：与 D4（可配置处置动作）解耦，本批不做自动减半仓/清仓；避免在盘中自动卖出引入不可逆风险。
3. **账户级状态用 `live_sessions.account_risk_state` 单列存 JSON**：账户维度没有天然子表，新建单行表反而多一次 join；JSON 只用引擎读写，不参与查询。
4. **D3 应用时机放在 `start_session` 而非每次 `_handle_bar`**：运行中改参数必须显式重启才生效，避免「以为改了、实际没改」；未运行会话立即应用，减少一次无意义重启。
5. **M2 用独立单行表而不是 config 文件**：应急开关必须能被 API 立即改写并跨重启保持，config 文件写回会污染用户手工配置；单行表读写成本可忽略。
6. **「一键全平」不绕过既有提交链**：只生成 `CLOSE` 意图走 `_submit_one_order`，熔断/时点/在途/T+1 照常生效；本批不实现「强制按市价清仓」。


### 批次 7（D4、D5、D6、M4）

**D4 熔断处置动作可配置**
- 表/列：迁移 `d0e1f2a3b4c5` 给 `portfolio_strategies` 加 `breaker_action`（默认 `halt`，不改既有行为）：`notify` / `halt` / `half` / `liquidate`；白名单校验（API 400）。
- 内核：`PortfolioRiskManager` 在回撤/日亏新触发时置 `pending_disposal`；`Portfolio.on_bar` 消费一次并生成 SELL（`half` 按整手向下取半、不足一手跳过；`liquidate` 全平），回测/实盘同源（回测下一 bar 开盘成交，实盘当根提交）。
- 口径：`breaker_action` 写入 `PARAMS_SNAPSHOT_FIELDS` + `params_snapshot`，参与增量指纹；默认 `halt` 时订单列表与改动前逐字一致。
- 语义：`notify` 仍停开仓但不自动减仓（只额外落一条 `gate=breaker_action/action=notify` 决策事件）；`half`/`liquidate` 的卖单再受 T+1、停牌、跌停等既有闸门约束。
- 回退：默认 `halt`；回测/实盘均不生成处置单。

**D5 手动恢复原因记录与二次确认**
- API：`POST /api/live/sessions/{id}/portfolios/{pid}/recover` 接受可选 body `{reason, confirm}`；返回体带 `reason` 回显。
- 二次确认：`circuit_breaker_count >= 3` 或 `risk_state.manual_recovery=true`（已转手动恢复）时必须 `confirm=true`，否则 body `code=400`、提示「需二次确认」，且不改任何状态；其余场景（未转手动恢复的普通熔断）沿用一键恢复，不新增操作负担。
- 审计：恢复成功后写 `live_decision_events`（`gate=breaker_recover`、`layer=portfolio_risk`、`action=recover`、`portfolio_id`、`message` 含原因），运行中/未运行 session 都落库，复盘可按 gate 过滤。
- 兼容：不传 body 的旧调用在普通熔断下行为不变；仅已转手动恢复的旧调用会得到 400，需补 `confirm=true`（前端已按此提示）。
- 回退：删 body 解析与审计写入即可回到直接清零；迁移无涉及。
